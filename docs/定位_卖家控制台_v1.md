## 一、定位声明

**一句话**：

> 一个**面向卖家的经营控制台**：卖家在同一处管理**商品陈列、商品管理、售后处置**三件事——
> 既可**手动**完成全部操作，也可**只对 AI 助手说一句话**，由它调用对应工具替他完成。
> 售后处置是其中的**一个功能模块**（首个已完成的模块），不再是项目主干。

**用户原始表述**（2026-10-16 给定，保留原文以免二次转述失真）：

> 修改项目的定位是对接业务，而不是作品展示……当前的项目保留但不再是主干而是一个功能，修改为面向卖家的控制台。
> 1、前端改为左、中、右、智能AI助手对话入口（小标）三栏+可拖动图标，左侧栏有商品陈列、商品管理、售后。
> 2、商品陈列是展示上架商品的展示，商品管理是能够对所有商品进行删改查、新增商品，售后就是当前项目的功能。
> 商品陈列部分要涉及上传商品宣传图、文案、定价，所以设计成卖家可以自己手动上传、编写文案、设置定价，
> 也可以使用AI模型通过与AI进行对话让模型自己进行将卖家提供的图片设置成宣传图生成编辑对应的文案、编辑定价。
> 商品管理部分卖家可以自行手动操作进行增删改查，同时删除商品陈列部分的对应内容，
> 也可以通过与AI进行对话让模型自己进行对应增删改查的操作。售后部分暂时按当前项目，后续再做版本迭代。
> 智能AI助手部分：卖家可以点击这个AI助手，只通过自然语言就能让AI调用对应部分的工具对上述三部分的功能进行操作。

## 二、模块划分：三个业务模块 + 一个支撑模块

| 模块 | 是什么 | 数据视角 | 本轮范围 |
| --- | --- | --- | --- |
| **商品陈列** | 展示**已上架**商品的对外样貌：宣传图、文案、价格 | **上架商品**的展示视图 | 手动编辑 + AI 生成文案/定价（**生图留下一轮**） |
| **商品管理** | 对**全部商品**做增删改查（含上架/下架） | **全量商品**的操作视图 | 完整 CRUD + 图片上传 |
| **售后** | 现有售后处置能力：收件箱 → 指派/接管 → 判定 → 人工处置 | 售后事件（工单） | **按当前实现原样嵌入**，逻辑不改，后续版本再迭代 |
| **知识库**（支撑） | 卖家上传的**店规原文**：售后政策 / 平台规则 / 发货时效 / 商品资料 | 卖家自有文档 | 上传（文本类 + 截图 OCR）/ 分知识库与标签 / 试检索 / 删除与改归属 |

**知识库为什么是"支撑"而不是第四个并列业务**：它本身不产生业务动作，只回答"我们店自己是怎么规定的"。
它存在的唯一理由是——在此之前助手只知道「商品现在什么价」，不知道**店里的规矩**，
被问「我们退货怎么规定」时只能凭常识编。这与售后判定链路的「逐条依据 + 同输入同结论」是同一条原则：
**答案必须能指回原文**，而不是模型觉得合理。

### 关键设计推论（请确认这一条）

用户表述中"商品管理……同时删除商品陈列部分的对应内容"说明：
**「商品陈列」与「商品管理」是同一份商品数据的两个视图**，不是两套数据。

- 管理里删除 / 下架 → 陈列里同步消失；
- 陈列里编辑文案/定价 → 管理里同步可见。

因此实现上**只有一张商品主表**，两个模块只是不同的呈现与操作入口。这避免了"两处真相"。

## 三、AI 助手：本方案的核心新增

**它不是一个聊天窗口，而是一个能动手的"经营助手"**——这是本项目与前四次改向最实质的差别。

| 维度 | 说明 |
| --- | --- |
| 入口 | 右下角**可拖动的浮动图标**（"小标"），点击展开对话抽屉；不占用三栏 |
| 能力 | 用自然语言下达指令，助手**调用对应模块的工具**完成操作（查询 / 新建 / 修改 / 删除商品、生成文案、给定价建议） |
| 懂店规 | 回答"我们退货怎么规定"时**先检索知识库**，按原文回答并说明出处；资料里没写就如实说没找到，**不许用常识补一套规则** |
| 上下文 | 助手知道"卖家当前在哪个模块、选中了哪个商品"，避免"你要改哪个"的来回追问 |
| 内核 | **复用现有 agentic 循环**（手写 tool-calling 循环，`app/chat/agent.py`），把工具集从"售后专用"泛化为**按域组织的工具注册表** |
| 破坏性动作 | 删除 / 下架等**必须人在环确认**：助手提出动作 → 界面弹确认 → 卖家点确认后才执行（与售后"资金动作需人工确认"同一套原则） |

## 四、为什么这次改向比前四次更站得住

此前我诊断过一个死结：

> 面向商家/卖家的产品需要**真实数据源、真实卖家**，个人项目验证不了 → 于是靠"再加一个功能"换确定感 → 项目变重 → 更无法验证。

**这次的设计解开了它**：商品数据**由卖家自己录入**（上传图、写文案、定价格），
数据源不再是"外部电商平台"，而是**自产闭环**。因此：

| 环节 | 数据来源 | 可验证性 |
| --- | --- | --- |
| 商品陈列 / 商品管理 | **卖家自建** | ✅ 完全可控 |
| AI 文案 / 定价建议 | 模型基于卖家输入生成 | ✅ 可当场演示 |
| 售后 | 沿用现有仿真夹具（沿用既有边界声明） | ⚠️ 仍无真实业务 API |

**结论**：这次改向不是又一次"换业务场景"，而是**把能力装进一个自带数据的容器**。

## 五、验收标准（改向后的新口径）

前一版是"作品档位"，验收只问"可演示 / 可复现 / 边界清晰"。**现在改为对接业务，验收标准随之调整为三条**：

| # | 标准 | 说明 |
| --- | --- | --- |
| 1 | **一条链路能真跑通** | 卖家手动录一个商品（图 + 文案 + 价）→ 出现在陈列 → 在管理里改价 → 陈列同步 → 删除后两处同时消失 |
| 2 | **AI 能代替手动完成同一件事** | 对助手说一句话即可完成上面链路中的任意一步，且**破坏性动作有确认**；一句话里含**多件事**时（「建商品 + 配图 + 写文案」），确认卡是**一张、点一次全部执行**，执行完逐项如实汇报（含失败与未做的） |
| 3 | **售后模块不受影响** | 现有售后全链路（含接管/退回/结案）在新控制台内仍可完整操作 |
| 4 | **知识库链路能真跑通** | 传一份政策 → 页面上搜得到 → 问助手"我们退货怎么规定"，它引用该资料原文并说明出处 → 删掉该资料后再问，它如实说"资料里没找到" |

> **不再使用"效率数字"作为验收标准**（介入率、时长等仍需真实业务量才能测），
> 但仍**允许且要求**展示"人工 6 处 → 2 处"这类**可当场演示的流程对比**。

## 六、边界声明（明确不做）

| 不做 | 原因 |
| --- | --- |
| ~~**多卖家登录与数据隔离**~~ | ✅ **已实现（2026-10-20）**：账号 + 会话 + 浮窗登录；所有 `/api/seller/*` 要求登录，数据按 `seller_id` 隔离；**每次登录默认开启新对话**（会话自带助手线程）。仍不做：自助注册、找回密码、第三方登录 |
| **AI 生成宣传图** | 需新增图像生成模型依赖；本轮先做**文案 + 定价**，生图留下一轮 |
| **接入真实电商平台 API** | 无授权、无客户；商品数据由卖家自建（见 §四） |
| **把"规则写不成表"的业务纳入** | 与售后模块同一原则：输入明确、结论可枚举、规则可成表 |
| **生产级鉴权 / 审计合规改造** | 单卖家本地形态，鉴权缺口在文档中显式声明，不假装已具备 |
