> **定位**：在《方案 v3.2 方向稿》之上，**新增"执行层"**——把智能体从"对话助手"升级为"**能自主办事的 Agent**"。
> **触发**：用户明确「核心是开发智能体，让智能体**真正自主调用工具去处理解决事务**，倾向做售后 Agent 产品」。
> **状态**：**方案，待确认**。涉**资金/法律动作**，红线分级（§四）须用户拍板后才可实施（纪律 10）。
> **日期**：2026-10-15


> ⚠️ **已并入《方案_商家售后智能体_v4.md》§五（执行层红线分级）。本文档保留作为执行层的详细说明。**

---

## 一、一句话定位

**在售后流程里放一个"能自主办事"的 Agent：它理解诉求 → 自主规划（查什么、做什么、按什么顺序）→ 直接执行事务（退款/补发/换货/补偿）→ 处理结果与异常 → 汇报。**
确定性不消失，只是从"模型被禁止碰结论"升级为"**模型自主发起动作，确定性闸门约束动作上限，人工兜底超限与争议**"。

---

## 二、与 v3.2 的差异（增量，不是推翻）

| 维度 | v3.2（助手） | 本方案（办事者） |
| - | --- | --- |
| 模型能做什么 | 聊、查、取证、转交规则/人工 | 上述 + **自主执行事务** |
| 资金动作 | 规则+双闸门；**模型不得直接触发** | 模型可**发起**，但受**分级授权 + 确定性闸门 + 人工兜底**约束 |
| "赔不赔/赔多少" | 规则+人工 | 规则（额度内）自动通过的部分，agent 可**直接落地执行** |
| 处置层 | `DISPOSAL_ENABLED=false` + `SHADOW_MODE=true`（从未执行） | 分级激活（§四） |

> **不变**：判定链路（R1—R8 / 审计 / HITL / 双闸门）**原样复用**，降级为 agent 调用的工具；"同输入同结论"仍只约束判定。

## 三、场景地图（从"仅退款"扩到"售后全场景"）

| 场景 | 判定确定性 | 是否需要协商 | 执行动作 | agent 价值 |
| - | --- | --- | --- | --- |
| 仅退款（不退货） | 高（规则可判） | 否 | 退款单 | 低→中 |
| 退货退款 | 高（退货物流可验） | 否 | 退货单→退款 | 中 |
| 补发 / 重发 | 中（物流损坏/漏发） | 否 | 补发单 | 中 |
| 换货 | 中 | 否 | 换货单 | 中 |
| 部分退款 / 差价补偿 | 低 | **是（协商金额）** | 补偿单/券 | **高（模型真价值）** |
| 价保 | 高（结构化） | 否 | 价保单 | 低 |
| 质量争议 | 低 | **是** | **转人工**（红线） | 人工 |

> **核心观察**：agent 的自主价值在"**部分退款/补偿协商**"这类场景最大——但这恰恰是资金风险最高、最需要闸门的地方。**分级授权（§四）就是为此设计。**

---

## 四、⚠️ 红线分级方案（**核心决策，须你拍板**）

把"执行动作"按 **金额 × 确定性 × 风险** 分三级，逐级决定 agent 的自主边界：

| 级别 | 触发条件 | agent 权限 | 兜底 |
| - | --- | --- | --- |
| **L1 全自主** | 规则判定 `auto_pass` 且金额 ≤ `AUTO_AMOUNT_CAP`（现 ¥300，复用 R1）且无风险标签、无争议 | 直接执行：退款 / 补发 / 发券 | 每笔落审计；T+1 前可撤销；事后抽样复核 |
| **L2 需确认** | 规则通过但金额在中区间（如 300~2000）或 首次/异常/画像存疑 | agent 发起动作并**挂起**，待人工确认后执行 | HITL（复用现有 `interrupt` + 人工介入台） |
| **L3 禁止自主** | 质量争议 / 大额（>阈值）/ 法律敏感 / 买家威胁投诉 | **只能转人工**，不得发起任何资金动作 | 人工全权 |

> **三条硬线（不可让步，除非你明确要改）**：
> 1. **规则引擎仍是判定唯一来源**——模型只"请求判定 + 执行落地"，**不参与"赔不赔/赔多少"的判定**；
> 2. **执行动作永不 mock 成功**——处置层失败必须升级人工（延续 M2 读/写通道语义）；
> 3. **每笔资金动作必须幂等 + 可审计 + 可撤销**。

## 五、工具分层（执行层新增 5 个"写/资金"工具）

| 层 | 工具 | 授权级别 | 约束 |
| - | --- | --- | --- |
| 读（自由） | 查订单 / 查物流 / 查历史售后 / 查商品 / 查券 / 查价保 | 任意 | 只读；取不到返回"未获取到"，不编造 |
| 判定（可调） | 提交判定（调用现有规则图） | 任意 | 结论由规则给出，模型不改写 |
| **执行（分级）** | `create_refund` / `create_reshipment` / `create_exchange` / `issue_compensation` / `create_ticket` | **L1/L2 见 §四** | 幂等键=受理号；独立限流；失败升级人工 |
| 禁止 | 直接退款绕过审计 / 改规则 / 改阈值 / 任意 SQL / 任意 URL | — | **绝不暴露给模型** |

> **执行工具对模型是"发起一个动作"，不是"打钱"**：`create_refund` 内部走既有处置层（双闸门 + 幂等 + 审计），
> 模型拿到的只是一个"结果引用 + 状态"，**永远接触不到资金通道本身**。

---

## 六、安全闸门（执行层必须同时具备，缺一不可）

| 闸门 | 内容 | 来源 |
| - | - | - |
| 幂等 | `Idempotency-Key = 受理号`；重复提交返回既有结果 | 复用 M2 |
| 双闸门 | `SHADOW_MODE=false` **且** `DISPOSAL_ENABLED=true` 才具备执行资格 | 复用 M2 |
| 限流 | 执行层**独立信号量**（并发 3），与取数共用隔离 | 复用 M2 |
| 失败语义 | 执行失败**绝不假成功** → 升级人工；`reason` 区分 `rule_to_human` / `disposal_failed` | 复用 M2 |
| 审计 | 每笔资金动作落 `decision_audit`（含发起人=agent、动作、金额、时间、结果） | 复用 + 扩展 |
| 撤销 | L1 动作 T+1 前可撤销（补偿/退款未到账前可拦截） | 新增 |
| 预算 | 复用成本闸门（额度/预警/月度上限） | 已实现 |

## 七、实施分期

| 阶段 | 内容 | 关键产出 | 计费 |
| - | --- | --- | --- |
| **P1.5** | **红线分级落地 + 执行工具骨架**：L1 全自主（仅退款，≤¥300）打通「判定→执行→审计→可撤销」，**仍用 mock 处置通道 + 影子模式验证** | agent 真正"办成一笔退款"的端到端链路 | 否（桩 + mock） |
| **P2** | 人工介入台改造（卷宗 + 会话还原 + 人工确认 L2） | 仲裁员可对 L2 动作一键确认/驳回 | 否 |
| **P3** | L2 半自主 + 部分退款/补偿协商场景 + 视觉证据 | 协商类场景跑通，模型价值释放 | 视预算 |
| **P4** | 接真实处置接口（真实退款/补发通道）+ 真实订单/物流 | 真实事务落地 | 视接入 |

> **P1.5 是"从助手到办事者"的关键一跳**：它在**影子模式下**证明"agent 能自主发起并落地一笔受控事务"，
> **零真实资金动作、零模型调用**（桩验证）。真实处置接口留到 P4，仍需单独授权（纪律 10）。

## 八、风险披露（纪律 10，须你知悉）

| 风险 | 说明 | 缓释 |
| - | - | - |
| **资金损失** | agent 误执行退款/补偿 | L1 仅限规则 `auto_pass` + 小额定；可撤销；抽样复核 |
| **法律/合规** | 自动退款若处理不当可能引发纠纷 | L3 质量/大额/敏感一律人工；全程审计可追溯 |
| **模型越权** | 模型可能"骗取"执行工具 | 工具**不暴露资金通道**；白名单二次校验；执行层二次授权校验 |
| **重复/并发** | 同单重复执行 | 幂等键 + 唯一约束 + 独立限流 |
