## 一、P1 交付边界

**做**：单工单对话闭环（网页 H5）· 4 个读工具 + 2 个写/升级工具 · 提交判定（调用现有图）·
结论解释 · 护栏（20 轮 / 200 字）· **成本闸门** · 对话级审计 · 会话数据落库。

**不做**：视觉理解（P3）· 真实生产库（P4）· 商家侧 · 小程序 / IM · 多语言 · **把结论交给模型**。

---

## 二、总体结构

```
L1  H5 对话页（买家）
      │  SSE（流式回复）
L2  对话内核
      ├─ 护栏（轮数 / 字数 / 路由到人工）
      ├─ 成本闸门（调用前预检 + 调用后记账）
      ├─ agentic 循环（模型 ⇄ 工具，手写 StateGraph）
      ├─ 记忆（会话上下文 + 工单阶段）
      └─ 槽位抽取 + 参数装配
      │  调用工具 submit_for_decision
L3  判定后端（**v2.x 现有图原样复用**）
      intake → 取数 → 举证 → judge → risk → dispose → audit
      │  返回：结论 + 命中规则 + 逐条依据
L4  数据层
      conversation_message / case_slot / guardrail_event（新增）
      decision_audit（加 3 字段）· checkpointer（沿用）
```

**关键约束**：L2 只能通过 `submit_for_decision` 触达 L3，**不得直接读判定内部状态**；
L3 不知道对话的存在（保持无状态、可复现）。

## 三、关键设计决策（含备选与理由）

| # | 决策 | 理由 | 备选（未采用） |
| - | --- | --- | --- |
| **D1** | 对话循环用**手写 LangGraph 子图**（`model_step` ⇄ `tool_step` + `guard`） | 需要在**每一次模型调用前**插成本预检、在**每一次工具调用后**落审计、并有**硬性终止条件**（20 轮）。手写节点才能把这三件事做成不可绕过 | LangChain `create_agent` + middleware：代码少，但护栏要靠 middleware 组合，**"绝不被绕过"难保证**；若后续护栏能全用 middleware 表达，可再评估 |
| **D2** | **会话 = 工单**：`case_id` 在**对话线程 / 判定图 `thread_id` / 审计**三处同值 | 卷宗、审计、一致率统计都要按同一键串联 | 会话与受理号分离（需额外映射，人工介入时要跨表查） |
| **D3** | 槽位**只用于"填表"**，判定仍由规则；**缺必填槽位不得猜测** | 模型抽取是"推断"，一旦参与判定就破坏可复现 | 让模型直接产出结论（红线性否决） |
| **D4** | 买家陈述与权威数据冲突时**以权威数据为准**，并**记录冲突** | 例：买家说"没收到"但物流已签收 → 交规则/人工，不由模型调和 | 由模型自行判断孰对（不可复现、不可追责） |
| **D5** | 成本闸门 = **调用前预检 + 调用后记账** | 只在记账侧管，会出现"已经花了才发现" | 仅事后统计（无法止损） |
| **D6** | 回复用 **SSE 流式**；上传走普通 POST | 对话体验需要逐字出；上传不必流式 | 轮询（体验差） |

## 四、会话状态机

| 状态 | 含义 | 可迁移到 |
| - | --- | --- |
| `CREATED` | 已建会话，未开始 | `CLARIFYING` |
| `CLARIFYING` | 正在澄清诉求与事实（多轮） | `COLLECTING` / `SUBMITTED` / `ESCALATED` |
| `COLLECTING` | 正在收证据 | `SUBMITTED` / `ESCALATED` |
| `SUBMITTED` | 已提交判定，等待结论 | `DECIDED` / `ESCALATED` |
| `DECIDED` | 已出结论并已告知买家 | `CLOSED` |
| `ESCALATED` | 已转人工（终态，等人工） | `CLOSED` |
| `CLOSED` | 结束（含超时关闭） | — |

**迁移守卫（全部为硬条件，任一不满足即不放行）**：
1. 会话轮次 < 20；
2. 成本闸门未暂停；
3. 会话未处于终态。

**升级到人工（ESCALATED）的触发源**（每个都必须写明原因并落 `guardrail_event`）：
轮数耗尽 · 字数二次超长 · 成本闸门暂停 · 判定返回 `to_human` · 工具连续失败 · 买家主动要求（"转人工"）。

## 五、护栏实现点

| 护栏 | 检查时机 | 触发动作 | 留痕 |
| - | --- | --- | --- |
| 轮数 ≤ 20 | **每次收到买家消息时**（增量校验） | 第 20 轮：**能给结论就给结论并结束；否则转人工**，明确告知"已转人工，请等待" | `guardrail_event(type=round_limit)` |
| 单条 ≤ 200 字 | 收到消息时（在计轮之前） | 首次：提示精简，**不计轮次**；再次：转人工 | `type=msg_too_long`（含第几次） |
| 成本预警（¥0.1 等效消耗） | **每次模型调用前** | 立即暂停**新会话**；进行中会话允许收尾 | `type=cost_warning` |
| 月度上限（¥200） | 同上 | 同上（更严格，含进行中会话收尾） | `type=cost_cap` |
| 工具调用次数 | 每轮内 | 单轮内工具调用 ≤ N（建议 3），超过强制结束本轮 | `type=tool_limit` |
| 澄清次数 | 每次追问 | 同一槽位追问 ≤ 2 次，仍拿不到 → 转人工 | `type=slot_missing` |
| 会话静默超时 | 定时任务 | 建议 24h 无消息 → 自动收尾（有结论则告知，无则转人工） | `type=session_timeout` |

> **需要澄清两处口径**（见 §十四 待确认 T2/T3）：
> ①「1 轮」是**一个往返**（买家消息 + 智能体回复）还是**一次模型调用**？（建议按往返计，审计按模型调用计）
> ② 会话静默超时的时长（建议 24h）与到期动作。

## 六、成本闸门设计（P1 第一个实现的东西）

### 6.1 计量
- **口径**：`input_tokens` / `output_tokens` × **官方单价** → **等效消耗金额**；单价入 `.env`（纪律 9）。
- **记账**：每次模型调用后写一条用量记录（含 `case_id` / 轮次 / 模型 / token / 金额 / 时间）；
  月度累计 = 当月求和（不另建汇总表，避免两份真相）。

### 6.2 三级动作
| 级别 | 阈值 | 动作 |
| - | --- | --- |
| 免费额度优先 | qwen3.7-plus 100 万 token / 90 天 | 额度内优先消耗；**额度余额按本地累计估算** |
| **预警线** | **¥0.1（等效消耗）** | **立即暂停新会话 + 汇报** |
| 月度硬上限 | ¥200 | 停用对话入口（转人工兜底） |

### 6.3 暂停语义（必须写死）
- **新会话**：拒绝创建，返回明确提示（不静默失败）；
- **进行中的会话**：**允许收尾**——能出结论就出结论，否则直接转人工；
- **健康检查**：暴露 `cost_gate = active|paused` 与当月累计额度消耗。

### 6.4 汇报通道
审计 + 日志 + 健康端点。（如需邮件 / IM 通知，请指定通道——P1 默认不做外发。）

### 6.5 两个不确定项（诚实标注）
1. **免费额度余额是否可通过 API 查询**——未核实。设计上先按**本地累计估算**，并保留人工与控制台账单核对的入口；
2. ~~¥0.1 的口径~~ → **已确认为「等效消耗」**（2026-10-14）。⚠️ 后果：量级很小，**首次联调即可能触发暂停**，
   须提供**受控放宽**手段（改 `.env` + 重启，且每次放宽均记入日志与审计）；
   **单价必须配置**（`PRICE_INPUT_PER_1K` / `PRICE_OUTPUT_PER_1K`），未配置则闸门降级为"仅计量 token、不判金额"。

## 七、工具清单（P1 六个）

| 工具 | 类型 | 入参（摘要） | 返回（摘要） | 失败语义 |
| - | --- | --- | --- | --- |
| `query_order` | 读 | `case_id` | 订单金额、商品、物流状态、签收时间 | 取不到 → 返回"未获取到"，**不得编造** |
| `query_logistics` | 读 | `case_id` | 轨迹摘要、签收状态 | 同上 |
| `query_case_progress` | 读 | `case_id` | 当前阶段、已提交材料、时限 | 同上 |
| `register_evidence` | 写 | `case_id`、材料引用列表 | 登记结果、有效数量 | 幂等（同引用不重复登记）；失败不谎报成功 |
| `submit_for_decision` | 判定 | `case_id`、装配后的申请单 | 结论 + 命中规则 + 逐条依据 | 失败 → 保留会话状态，可重试；连续失败 → 转人工 |
| `escalate_to_human` | 升级 | `case_id`、原因码 | 受理结果 | 失败重试；**不可静默失败**（否则用户以为已转人工） |

**禁止暴露给模型**：退款 / 打款 / 改规则 / 改阈值 / 任意 SQL / 任意 URL 抓取。
**每个工具都记审计**：谁触发（模型）、入参摘要、耗时、结果摘要、是否成功。

## 八、槽位抽取与参数装配

- **槽位（8 个，写入 `case_slot`）**：诉求分类 · 问题对象 · 问题现象 · 影响数量 · 期望方案 ·
  签收后时长（可由订单推） · 已提交材料 · 补充说明。
- **每个槽位必须存"来源轮次"**——卷宗里要能点回原话（卷宗 §二 ⑥ 的要求）。
- **装配规则**：
  1. 必填槽位（诉求分类、问题对象、期望方案）缺失 → **继续追问**（受"同槽位追问 ≤2 次"约束），不得猜测；
  2. 装配出的申请单里，**金额、物流状态等权威字段以取数层为准**，槽位只提供"原因/诉求"类字段；
  3. 冲突（买家陈述 vs 权威数据）→ 记录 `conflict` 标记，交规则判定与人工。
- **红线**：槽位**不进入**规则事实字典（`FACT_FIELDS` 不放槽位）——物理上杜绝"推断参与判定"。

## 十一、H5 对话页结构（组件清单，不含代码）

```
[订单卡片]  商品 · 订单号 · 申请金额 · 物流 · 剩余时限
[消息列表]  富消息：文本 / 图片 / 金额卡片 / 快捷选项按钮
[进度条]    已受理 → 待补证 → 待人工 → 已出结论（带时间戳）
[输入区]    文本框（实时字数提示 200 上限）+ [上传证据] [转人工]
[提示条]    护栏反馈：超长提示 / 已转人工 / 会话已结束
```

**必须实现的三类反馈**（对应 §五 护栏）：
1. 超长：`"内容较长（xxx 字），请精简到 200 字内重发"`（**不计轮次**）；
2. 轮数耗尽：`"本次咨询已达上限，已转人工，请等待客服接入"`；
3. 成本暂停：`"系统当前暂停接待，已为您转人工"`。

## 十六、风险与回退

| 风险 | 影响 | 缓解 |
| - | --- | --- |
| 模型乱调工具 / 反复追问 | 体验差、成本高 | 单轮工具上限、同槽位追问上限、轮数硬上限 |
| 槽位抽取错误 | 装配出错 → 结论偏差 | 槽位不参与判定；冲突以权威数据为准；卷宗标"推断" |
| 成本失控 | 真金白银 | 闸门前置预检；实测调参 |
| 对话历史含个人信息 | 合规 | 90 天保留；脱敏；模型调用可全局关闭 |
| 与现有判定图耦合 | 破坏可复现 | 只允许通过 `submit_for_decision` 调用；判定图不读对话状态 |

**回退**：P1 全部新增在独立前缀与独立表下；**关闭 `LLM_ENABLED` 即可退回现有控制台形态**，判定链路不受影响。
