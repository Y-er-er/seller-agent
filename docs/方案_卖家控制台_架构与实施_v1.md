## 一、信息架构（前端）

### 布局

```
┌──────────────────────────────────────────────────────────────┐
│ 顶栏：品牌 · 连接状态 · 实时状态 · 刷新                        │
├──────────┬────────────────────────────┬──────────────────────┤
│ 左栏      │ 中栏：主内容区              │ 右栏：详情 / 编辑     │
│ 模块导航  │ （随模块切换）              │ （选中项的详情与表单） │
│          │                            │                      │
│ 商品陈列  │  商品卡片网格               │ 商品详情 / 编辑表单   │
│ 商品管理  │  商品表格（全量）           │ 商品详情 / 编辑表单   │
│ 售后      │  工单收件箱（复用现有）      │ 工单详情（复用现有）  │
│          │                            │                      │
│          │                    ╭───────┴──────────╮           │
│          │                    │ 🤖 浮动 AI 助手   │ ← 可拖动   │
│          │                    ╰──────────────────╯           │
└──────────┴────────────────────────────┴──────────────────────┘
```

- **左栏**：模块导航（概览 / 商品陈列 / 商品管理 / 售后 / 操作日志），带条目数角标。
- **中栏**：主内容区，随模块切换（概览看板 / 卡片网格 / 表格 / 工单收件箱 / 日志表）。
- **右栏**：**上下文详情面板**——内容随「当前模块 + 选中对象」变化，**不是固定的"编辑商品"**。
- **AI 助手**：右下角**可拖动**的浮动图标（"小标"），点击展开**对话抽屉**；抽屉从右侧滑出，不占三栏。

### 右栏的职责（易错点，务必按此实现）

> ⚠️ 原型 v1 曾把右栏写死为"编辑商品"，切到概览/日志时仍是商品表单——这是一个真实的信息架构缺陷，v2 已修正。
> 实现时必须按模块渲染，不得硬编码。

| 模块 | 右栏内容 | 未选中时 | 底栏按钮 |
| --- | --- | --- | --- |
| **概览** | **不显示右栏**（全宽看板） | — | — |
| **商品陈列** | 商品详情 · **陈列预览**（买家视角小卡 + 图片 / 文案 / 价格 + 陈列设置：置顶与排序） | 空态引导 | 保存 / 重置 |
| **商品管理** | 商品详情 / 编辑（**全字段**：成本 / 库存 / 预警 / 类目 / 状态 + 删除） | 空态引导 | 保存 / 重置 / **删除商品** |
| **售后** | **不显示右栏**（iframe 自带三栏） | — | — |
| **操作日志** | **变更详情**（时间 / 来源 / 动作 / 对象 + **改前 → 改后** 对比） | 空态引导 | **撤销这次改动** |

两个要点：

1. **陈列与管理共用同一个商品面板**，靠"视角"控制字段显隐——陈列视角只看对外展示相关（预览 + 图/文案/价 + 陈列设置），管理视角才出现成本、库存、状态与删除。这样避免维护两套表单。
2. **切换模块时清空选中**，避免出现"在商品管理页看到商品陈列页的选中态"这类残留。

> **知识库为什么不用"独立服务"**：卖家上传的是**几十页规则文档**，量级完全在单机 Chroma 之内，
> 引入向量数据库服务只会让"启动就能跑"变成"先起三个容器"。存储层抽在 `store.py`，
> 将来换成外部向量库只需替换这一层。
>
> **卖家隔离落在 metadata**：每个分块带 `seller_id`（`kb` 为可选第二维），
> 所有检索/清单都带 `where` 过滤；越权删改一律报"不存在"，不暴露"这份资料不是你的"。

> **可插拔适配层**（`ports/` + `adapters/`）的完整设计见 `设计_可插拔适配层_v1.md`：
> 业务数据源 / 对象存储 / 模型三者抽为端口，开发期用 mock·local·stub，生产期换 http·cos·qwen。
> **图片存储不再单独写 `goods/storage.py`**——一律经 `ObjectStorage` 端口。

## 三、数据模型（MySQL 新增 4 张表）

所有表带 `seller_id`——这是用户要求的「**预留多卖家登录接口**」在数据层的落点。

```sql
-- 1. 商品主表（「商品陈列」与「商品管理」共用这一张）
CREATE TABLE goods (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  seller_id    VARCHAR(64)  NOT NULL DEFAULT 'default' COMMENT '预留多卖家',
  goods_no     VARCHAR(64)  NOT NULL                COMMENT '卖家可见编号',
  title        VARCHAR(200) NOT NULL,
  description  TEXT                                 COMMENT '文案',
  price        DECIMAL(10,2) NOT NULL DEFAULT 0,
  cost_price   DECIMAL(10,2) NOT NULL DEFAULT 0     COMMENT '成本价（算毛利，不对外展示）',
  stock        INT          NOT NULL DEFAULT 0      COMMENT '库存',
  stock_alert  INT          NOT NULL DEFAULT 0      COMMENT '低库存预警阈值，0=不预警',
  category     VARCHAR(64)                          COMMENT '类目',
  status       VARCHAR(16)  NOT NULL DEFAULT 'draft' COMMENT 'draft/on_shelf/off_shelf',
  cover_url    VARCHAR(512)                         COMMENT '宣传图（主图）',
  sort_no      INT          NOT NULL DEFAULT 0      COMMENT '陈列排序（越小越前）',
  pinned       TINYINT(1)   NOT NULL DEFAULT 0      COMMENT '陈列置顶',
  created_at   DATETIME     NOT NULL,
  updated_at   DATETIME     NOT NULL,
  UNIQUE KEY uk_goods (seller_id, goods_no),
  KEY idx_shelf (seller_id, status, pinned, sort_no),
  KEY idx_low_stock (seller_id, stock)
) COMMENT '商品主表：陈列=status on_shelf 视图，管理=全量视图';

-- 1b. 操作日志（人工与 AI 的动作都记；延续本项目「可审计」基因）
CREATE TABLE operation_log (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  seller_id   VARCHAR(64)  NOT NULL DEFAULT 'default',
  actor       VARCHAR(16)  NOT NULL COMMENT 'human（卖家）/ ai（助手）/ system（系统，如预警）',
  action      VARCHAR(48)  NOT NULL COMMENT '如 update_price / create_goods / delete_goods / bulk_update_price',
  target_type VARCHAR(24)  NOT NULL COMMENT 'goods / case',
  target_id   VARCHAR(64)  NOT NULL,
  summary     VARCHAR(255) NOT NULL COMMENT '人可读的一句话',
  before_json JSON                                  COMMENT '变更前（用于撤销）',
  after_json  JSON                                  COMMENT '变更后',
  undoable    TINYINT(1)   NOT NULL DEFAULT 0       COMMENT '是否可撤销',
  undone_at   DATETIME                              COMMENT '被撤销时刻，NULL=未撤销',
  created_at  DATETIME     NOT NULL,
  KEY idx_target (seller_id, target_type, target_id, created_at),
  KEY idx_actor (seller_id, actor, created_at)
) COMMENT '操作日志：谁在什么时候改了什么，AI 的动作同样留痕';

-- 2. 商品图片（宣传图可多张，首张为主图）
CREATE TABLE goods_media (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  seller_id  VARCHAR(64)  NOT NULL DEFAULT 'default',
  goods_id   BIGINT       NOT NULL,
  url        VARCHAR(512) NOT NULL,
  kind       VARCHAR(16)  NOT NULL DEFAULT 'cover' COMMENT 'cover/detail',
  sort_no    INT          NOT NULL DEFAULT 0,
  created_at DATETIME     NOT NULL,
  KEY idx_goods (goods_id, sort_no)
) COMMENT '商品图片；goods 删除时级联清理';

-- 3. AI 助手消息（与售后对话表分开，避免污染售后审计链）
CREATE TABLE assistant_message (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  seller_id  VARCHAR(64) NOT NULL DEFAULT 'default',
  thread_id  VARCHAR(64) NOT NULL,
  seq        INT         NOT NULL,
  role       VARCHAR(16) NOT NULL COMMENT 'seller/assistant/tool',
  content    TEXT,
  tool_name  VARCHAR(64),
  tool_args  JSON,
  created_at DATETIME    NOT NULL,
  UNIQUE KEY uk_thread_seq (thread_id, seq)
);

-- 4. 待确认的破坏性动作（人在环）
CREATE TABLE pending_action (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  seller_id  VARCHAR(64)  NOT NULL DEFAULT 'default',
  thread_id  VARCHAR(64)  NOT NULL,
  tool_name  VARCHAR(64)  NOT NULL,
  arguments  JSON         NOT NULL,
  summary    VARCHAR(255) NOT NULL COMMENT '给卖家看的一句话说明',
  status     VARCHAR(16)  NOT NULL DEFAULT 'pending'
             COMMENT 'pending/running（抢占执行中）/confirmed/failed/cancelled/expired',
  batch_id   VARCHAR(40)  NULL COMMENT '同一次请求的多个动作共享一个值 → 界面合成一张卡',
  created_at DATETIME     NOT NULL,
  decided_at DATETIME     COMMENT '决定时间；running 时写抢占时刻（用于判定执行是否卡死）',
  KEY idx_pending (seller_id, status),
  KEY idx_batch (batch_id)
) COMMENT 'AI 提出的破坏性动作，须卖家确认才执行';
```

**商品状态机**：`draft`（草稿）→ `on_shelf`（上架）⇄ `off_shelf`（下架）；删除＝硬删 + 级联删 `goods_media`。
建表脚本：`sql/goods_schema.sql`（与现有 `sql/chat_schema.sql` 并列，**不改现有表**）。

### 登录与鉴权（2026-10-20 落地）

原先"只预留接口位"的那一个函数，本轮按原设计**只改它**就接上了登录：

```python
# app/seller/deps.py
async def require_session(x_seller_token: str = Header(None)) -> SellerSession:
    """解析登录态：Token → (seller_id, thread_id, username)。无效/过期/已退出 → 401。"""

async def require_seller(session = Depends(require_session)) -> str:
    """只要 seller_id 的接口用它（数据隔离靠 seller_id）。"""
```

关键取舍：

| 议题 | 选择 | 理由 |
| --- | --- | --- |
| 身份怎么带 | `X-Seller-Token` **请求头** | 控制台可能用 `file://` 打开（origin=null）；跨源 Cookie 必须开 `allow_credentials`，而当前 CORS 是 `*`，两者不能共存。请求头没有这个矛盾。代价：Token 存 `localStorage`，XSS 可读 —— 本项目页面全部输出转义、无第三方脚本；若将来引入富文本，改回 HttpOnly Cookie |
| 密码怎么存 | PBKDF2-HMAC-SHA256，60 万次迭代，每账号随机盐 | 标准库即可（不新增依赖）；迭代次数写进哈希串，将来提高仍能校验旧哈希 |
| 失败怎么答 | 一律「账号或密码不正确」 | 区分"没这个账号"和"密码错"等于送一个账号枚举接口 |
| 暴力破解 | 同账号连续 5 次失败锁 10 分钟（**进程内**计数） | 单进程部署够用；多副本时各算各的 —— 这是已知边界，不假装是分布式限流 |
| 会话怎么失效 | `seller_session.revoked_at` / `expires_at`（数据库时间） | 退出要能**立即**踢下线，纯签名 Token 做不到；用 `NOW()` 而不是进程时钟，避免时区差导致"刚登录就过期" |
| 多账号数据 | 一账号绑定一个 `seller_id` | 业务表早就按 `seller_id` 隔离，登录只负责把"谁"解析成 id；新 `seller_id` 是一间空店（这是事实，界面不掩盖） |

**「每次登录默认开启新对话」怎么实现**：`seller_session.thread_id` —— 登录时新分配一条助手线程
（`t-<12 hex>`），助手所有端点（`chat/messages/reset/actions`）都从**会话**取 `thread_id`，
不再用常量 `"default"`。于是换一次登录就换一条线程，历史消息天然不会串进来，
**不依赖前端清状态**（刷新、换标签页都不会串回旧对话）。

配套：`sql/seller_schema.sql`（`seller_account` / `seller_session`）；
`scripts/create_seller_account.py` 供运维建号（**不开放自助注册** —— 注册出来的空店对卖家是误导）。

**已知边界（不假装已解决）**：

1. `GET /api/seller/uploads/{name}` **不要求登录** —— 它被 `<img src>` 直接引用，
   而 `<img>` 带不了请求头。要做就得改签名 URL 或 Cookie 会话，属独立改造。
   路径含日期 + `seller_id` + 32 位随机文件名，不可枚举。
2. 登录失败计数在**进程内**，重启清零；多副本部署时各算各的。
3. 没有找回密码 / 二次验证 / 登录审计日志（`seller_account.last_login_at` 只记最后一次成功时间）。

### 概览接口的取数成本（2026-10-20 修复）

**症状**：重启后端、刷新前端后，点左栏任一模块要等约 1 秒才换屏（"点了没反应"）。

**根因是三层叠加，不是某一处慢查询**：

| 层 | 问题 | 实测 |
| --- | --- | --- |
| 数据访问 | `connection.connect()` **每次查询新建一条 MySQL 连接**（无连接池），远程库对客户端做反向 DNS 解析，单次握手 ≈ 45 ms | `SHOW GLOBAL STATUS Connections` 计数 |
| 聚合口径 | `health_ranking` 逐商品查工单（N+1）：`for goods: await list_cases_by_goods(...)` | 27 件商品 → 27 条连接 / 1006 ms |
| 前端 | `refreshAll()` 六个请求**串行 await**，且本轮为修"左栏角标恒为 0"改成**每次都拉 `/overview`** | 改前 1801 ms / 41 条连接 |

**关键认知**：在这个环境里"每查询一次握手"意味着 **N+1 的代价是 N 次 TCP+认证，不是 N 次 SQL**。
所以它不只是慢，而是**随商品数线性恶化**：22 件时 `/overview` 946 ms，27 件时 1400 ms。

**改法**：

1. `chat_repo.aggregate_cases_by_goods(goods_nos)` —— 一条 `GROUP BY` 取回全部商品的
   `total / costly`（口径与 `_summarize()` 一致：赔付只算 `refund`/`reship`；`decision_result`
   为 NULL 计入分母但不计入分子）。`health_ranking` 改用它，**23 → 2 条连接**。
   单品页 `stats_for_goods` 仍走逐条查（只查一件，没有 N+1）。
2. 前端 `refreshAll()` 改 `Promise.all`：请求互不依赖，串行时每个都要先付一道固定开销。
   点击导航**先**更新左栏高亮与面包屑（纯本地计算）**再**取数 —— 数据没回来之前不重绘中栏，
   否则会闪一下"暂无商品"这种假信息。

**效果（同一台机器，交替 4 轮取中位）**：

| | `/overview` | 一次刷新（6 请求） |
| --- | --- | --- |
| 改前 | 1400 ms / 32 条连接 | 1801 ms / 41 条连接 |
| 改后 | **248 ms / 6 条连接** | **375 ms / 15 条连接** |

**仍然存在的成本（未做，需你决策）**：连接池。剩下每次请求仍要 ~45 ms×连接数，
6 条连接就是 ~270 ms 的主体。引入池（`DBUtils` 或自写）能把这块压到个位数毫秒，
但属**依赖变更**，未擅自加。另外 `conversation_case` 没有 `seller_id` 列，
`goods_no` 只在"同一卖家内唯一"，跨卖家重号会串数据 —— 这是既有隐患，本次未扩大也未修。

## 五、AI 助手（核心新增）

### 工具注册表（第一版）

工具自带元数据，助手据此决定能否直接执行。

| 工具 | 域 | 破坏性 | 说明 |
| --- | --- | --- | --- |
| `list_goods` | goods | 否 | 按状态/关键词查商品 |
| `get_goods` | goods | 否 | 单个商品详情 |
| `create_goods` | goods | 否 | 新建商品（默认 `draft`，不直接上架） |
| `update_goods` | goods | 否 | 改标题/文案/价格/类目 |
| `set_goods_status` | goods | 否 | 上架 / 下架 |
| `delete_goods` | goods | **是** | 删除商品 → **必须确认** |
| `generate_copy` | goods | 否 | 生成/改写文案（计费） |
| `suggest_price` | goods | 否 | 定价建议（计费） |
| `list_aftersale_cases` | aftersale | 否 | 查售后工单 |
| `get_aftersale_case` | aftersale | 否 | 工单详情（复用现有 `console.get_detail`） |
| `resume_aftersale_case` | aftersale | **是** | 退回智能体 → **必须确认** |
| `search_knowledge` | knowledge | 否 | 检索卖家上传的资料，返回带出处的原文（可 `kb` 限定知识库） |
| `list_knowledge_docs` | knowledge | 否 | 看有哪些资料（按知识库分组，含标签/片段数） |
| `delete_knowledge_doc` | knowledge | **是** | 删除一份资料 → **必须确认**；同名跨库时拒绝执行 |

> 知识库只有"检索/清单/删除"三个工具，**没有"改归属"**：让模型有权把资料挪来挪去，
> 只会制造"我明明放在售后政策库里"的困惑；归属由人在界面上改。上传也没有工具——
> 对话里模型拿不到文件字节（界面的回形针按钮负责收文件，入库后告诉助手即可）。

### 破坏性动作的在环确认（关键机制）

```
卖家：「把那个手机壳删了」
  ↓
助手：调用 delete_goods(goods_id=12)
  ↓ registry 判定 destructive=true
  ↓ 不执行，写 pending_action（status=pending）+ 返回给模型/界面
界面：弹出确认卡 ——「将删除商品「XX 手机壳」（¥199）及 3 张图片，不可恢复」
  ↓ 卖家点「确认」
POST /api/seller/assistant/actions/{id}/confirm → 真正执行 → 结果回灌对话
```

**为什么必须这样**：模型误判的代价不可逆（商品与图片一起没了）。这与售后里"资金动作必须人工确认"是同一条原则——**自主性在过程，确定性/不可逆动作在人**。

#### 多步 = 一张卡、一次确认（2026-10-20 修正）

卖家一句话常包含多件事（「生成宣传图、文案」），模型会提出**多个**待确认动作。
早期实现把它们渲染成**多张独立的卡**，实测出三个连环问题：

| 现象 | 真实原因 |
| --- | --- |
| 只点了一张，以为两件都做完了 | 每张卡各自一个确认按钮，界面没有"这一批共几步"的概念 |
| 点完一张，另一张"又弹出来" | 它一直都在，只是回复里用一句"文案已更新"盖过了"宣传图还在等确认" |
| 任务中心没有生图任务、商品也没有图 | 生图那张卡从未被执行 —— 不是执行失败，是**根本没跑** |

修正后的规则：**一次请求 = 一个批次 = 一张卡 = 一次确认**。

```
卖家一句话 → 模型提交 N 个需确认动作
  ↓ loop 给这一轮分配 batch_id，N 条 pending_action 共享它
界面：一张卡「这次有 N 步要你确认」+ 逐步列出（每步可单独划掉）
  ↓ 卖家点「确认执行这 N 步」
POST /api/seller/assistant/actions/batch/{batch_id}/confirm
  ↓ 逐项 抢占(pending→running) → 执行 → 落终态；失败项独立标记，不拖垮整批
  ↓ 汇总成一条消息写回对话 + **只续跑一次**模型（而不是每步各跑一轮）
```

两条配套的不变量：

1. **先抢占再执行**（`claim_action`）。`pending` 只是"还没做"，不是"只有我能做" ——
   连点两下会让两个请求都读到 pending、都去执行（生图重复计费）。
2. **剩余步骤必须由系统说出口**。只要系统里还有待确认项，回复末尾由代码追加
   「⏳ 还有 N 步在等你确认：…」，不依赖模型措辞（它可能说"已完成"），也不额外调模型。

### 「进行中」也是一种事实，同样不能由模型说

实测（2026-10-20）：卖家问「给电竞椅生成文案、以及宣传图」，助手回
「宣传图也在后台生成中，完成后会自动加到商品图片里」，但那一轮**一次工具都没调**，
`ops_task` 里也没有这条任务 —— 任务中心空着，商品也没有图。
来源是它自己上一轮说过的话（"还在等你确认"）被复述成了"在生成中"。

所以状态类陈述分三类，各有各的事实来源，**缺一不可**：

| 说法 | 事实来源 | 代码如何兜底 |
| --- | --- | --- |
| 「已发起 / 已弹出确认」 | `pending_action` 里应有 pending 行 | 无卡 → 纠正轮，逼它真调工具 |
| 「在后台生成 / 正在处理」 | `ops_task` 里应有 queued/running 行 | 无任务 → 纠正轮；仍嘴硬 → 代码追加「（系统核对）现在没有正在执行的后台任务…」 |
| 「文案已写入 / 价格已改」 | 商品表的实际字段 | 续跑时校验 `description` 是否真被写入 |

配套两条：

- **事实注入**：每轮开跑前把"进行中的后台任务数"读库塞进 system prompt
  （`build_system_prompt(..., unfinished_tasks=)`）。不注入，模型就会拿记忆当事实。
- **别再"作废"查不到工具的卡**：`confirm` 遇 `registry` 缺失时**不作废**
  （只 409 + 留一句人话）。作废不可恢复，而真正常见的成因是"进程里的注册表没跟上代码"
  （改了后端没重启）—— 作废等于把卖家的一次点击永久吞掉。

### 上下文注入

请求体带 `context`：

```json
{ "message": "把它的价格改成 99", "context": { "view": "goods_admin", "selected_goods_id": 12 } }
```

拼进 system prompt（"卖家当前在商品管理页，选中商品 #12（XX 手机壳，¥199）"），
避免"你要改哪个"的来回追问——**这是"懂上下文"与"只会聊天"的分界**。

### 上下文窗口：最近 N 条 + "末条必为本轮发言"

多轮对话必须限流（`HISTORY_LIMIT=40`），但**限流只能砍最早的，绝不能砍到本轮**。
这里踩过一个很贵的坑（2026-10-20）：`list_messages` 用 `ORDER BY seq ASC LIMIT 40`，
取到的是**最早**的 40 条。会话涨到 54 条后，窗口永远是 seq 1–40（末尾是"电竞椅文案"
那条工具消息），**卖家刚发的那句话根本没进模型** —— 模型只能接着窗口最后一句助手消息
往下写。表现是"答上一句"：

| 卖家实际说的 | 助手回的 |
| --- | --- |
| 售后政策中哪些不予受理？（连问 4 轮） | 电竞椅的文案已经成功更新到商品详情里了 ✅ |
| 给山地自行车归类 | 电竞椅的文案已经成功更新到商品详情里了 ✅ |

三条不变量（缺任何一条都会重现）：

1. **窗口取最近 N 条**：`SELECT * FROM (… ORDER BY seq DESC LIMIT n) t ORDER BY t.seq ASC`
   —— 先倒序截断、再正序回来。售后会话的 `chat_repo.list_messages` 是同一类写法，
   同样修（`limit` 之前也是取开头 20 条，超 20 条后买家新消息进不了模型）。
2. **窗口从卖家发言开始**：首条是 assistant 就往下裁——半截助手自述会让模型"接着自述"。
3. **本轮消息必须是最后一条且只出现一次**：代码兜底补一句 `{"role":"user", ...}`
   （已在历史末尾则不重复）。这条不变量让"模型看不到我刚说的话"在结构上不可能发生，
   即使将来窗口/清理逻辑再改也不会退化。

> 判据一句话：**"模型答的是上一句"先查上下文装配，再查提示词。**
> 提示词最多让它答偏，不可能让它答另一个话题；能答另一个话题，说明它没收到这一句。

### 智能体定位：决策 / 执行分层（2026-10-21 补记）

「意图与执行解耦（Plan-and-Execute）」落地后，一个必须说清的问题：**这还算是智能体吗？**
结论：算，而且是更合格的智能体——**智能在决策，从来不在执行**。

| 层 | 谁在做 | 做什么 |
| --- | --- | --- |
| **决策层** | 模型 | 理解卖家意图、拆解成步骤、判断哪些可立即做 / 哪些须确认、决定措辞与沟通 |
| **计划层** | `plan_batch`（模型产出结构化计划 + 代码展开） | 把"N 件商品的完整动作"压成一次调用，交给执行层 |
| **执行层** | 确定性代码 | 建品 / 改价 / 写回文案 / 抢占执行 / 落日志 / 失败重试，不靠模型"续跑" |

三个关键判断：

1. **function calling 里模型本来就没"亲手执行"过**。它只产出「工具名 + JSON 参数」，
   真正落库的是代码。把"执行"从模型手里拿走，不是拿走"智能"，是拿走它本就不该干的活。
2. **Plan-and-Execute 是业界成熟模式**（LangGraph 官方范式之一），不是自创。它与
   ReAct（边想边做）**不是替代关系，是按任务类型分工**：
   - **探索型 / 信息不足的任务**（"这个售后单能不能退"）→ ReAct，边查边想、临场调整；
   - **批量 / 结构已知的任务**（"建 50 件商品"）→ Plan-and-Execute，先出计划、代码批量执行。
3. **诚实声明边界**：批量场景确实收窄了"执行中途的临场决策"——但换来的是确定性、
   可审计（每步留痕）、可重试（失败项独立重置）、可扩展（不撞单轮工具预算）。
   在"人可复核、动作可撤销"的卖家控制台里，这是正确取舍。

对应的实现落点（本轮 P0/P1/P2）：

| 落点 | 机制 | 解决什么 |
| --- | --- | --- |
| `plan_batch` 工具 | 一次产出整批计划，确认类动作展开为同批 `pending_action` | 把 N×M 次工具调用压成 1 次，不再撞单轮预算 |
| `generate_copy(apply=true)` | 生成文案一步原子写回商品 | 去掉"模型再调 update_goods 续跑"的非确定性 |
| `batch_progress` / `retry_failed` | 进度按 status 聚合 + 失败项重置回待确认 | 进度可见、失败可恢复 |

## 八、风险与边界披露（须你知悉）

| # | 风险 | 处理 |
| --- | --- | --- |
