## 一、信息架构（前端）

### 布局

```
┌──────────────────────────────────────────────────────────────┐
│ 顶栏：品牌 · 连接状态 · 实时状态 · 刷新                        │
├──────────┬────────────────────────────┬──────────────────────┤
│ 左栏      │ 中栏：主内容区              │ 右栏：详情 / 编辑     │
│ 模块导航  │ （随模块切换）              │ （选中项的详情与表单） │
│          │                            │                      │
│ 商品陈列  │  商品卡片网格               │ 商品详情 / 编辑表单   │
│ 商品管理  │  商品表格（全量）           │ 商品详情 / 编辑表单   │
│ 售后      │  工单收件箱（复用现有）      │ 工单详情（复用现有）  │
│          │                            │                      │
│          │                    ╭───────┴──────────╮           │
│          │                    │ 🤖 浮动 AI 助手   │ ← 可拖动   │
│          │                    ╰──────────────────╯           │
└──────────┴────────────────────────────┴──────────────────────┘
```

- **左栏**：模块导航（概览 / 商品陈列 / 商品管理 / 售后 / 操作日志），带条目数角标。
- **中栏**：主内容区，随模块切换（概览看板 / 卡片网格 / 表格 / 工单收件箱 / 日志表）。
- **右栏**：**上下文详情面板**——内容随「当前模块 + 选中对象」变化，**不是固定的"编辑商品"**。
- **AI 助手**：右下角**可拖动**的浮动图标（"小标"），点击展开**对话抽屉**；抽屉从右侧滑出，不占三栏。

### 右栏的职责（易错点，务必按此实现）

> ⚠️ 原型 v1 曾把右栏写死为"编辑商品"，切到概览/日志时仍是商品表单——这是一个真实的信息架构缺陷，v2 已修正。
> 实现时必须按模块渲染，不得硬编码。

| 模块 | 右栏内容 | 未选中时 | 底栏按钮 |
| --- | --- | --- | --- |
| **概览** | **不显示右栏**（全宽看板） | — | — |
| **商品陈列** | 商品详情 · **陈列预览**（买家视角小卡 + 图片 / 文案 / 价格 + 陈列设置：置顶与排序） | 空态引导 | 保存 / 重置 |
| **商品管理** | 商品详情 / 编辑（**全字段**：成本 / 库存 / 预警 / 类目 / 状态 + 删除） | 空态引导 | 保存 / 重置 / **删除商品** |
| **售后** | **不显示右栏**（iframe 自带三栏） | — | — |
| **操作日志** | **变更详情**（时间 / 来源 / 动作 / 对象 + **改前 → 改后** 对比） | 空态引导 | **撤销这次改动** |

两个要点：

1. **陈列与管理共用同一个商品面板**，靠"视角"控制字段显隐——陈列视角只看对外展示相关（预览 + 图/文案/价 + 陈列设置），管理视角才出现成本、库存、状态与删除。这样避免维护两套表单。
2. **切换模块时清空选中**，避免出现"在商品管理页看到商品陈列页的选中态"这类残留。

| 文件 | 说明 |
| --- | --- |
| `frontend/seller.html` | 卖家控制台主页面（新入口，替换 `console.html` 成为主界面） |

## 三、数据模型（MySQL 新增 4 张表）

所有表带 `seller_id`——这是用户要求的「**预留多卖家登录接口**」在数据层的落点。

```sql
-- 1. 商品主表（「商品陈列」与「商品管理」共用这一张）
CREATE TABLE goods (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  seller_id    VARCHAR(64)  NOT NULL DEFAULT 'default' COMMENT '预留多卖家',
  goods_no     VARCHAR(64)  NOT NULL                COMMENT '卖家可见编号',
  title        VARCHAR(200) NOT NULL,
  description  TEXT                                 COMMENT '文案',
  price        DECIMAL(10,2) NOT NULL DEFAULT 0,
  cost_price   DECIMAL(10,2) NOT NULL DEFAULT 0     COMMENT '成本价（算毛利，不对外展示）',
  stock        INT          NOT NULL DEFAULT 0      COMMENT '库存',
  stock_alert  INT          NOT NULL DEFAULT 0      COMMENT '低库存预警阈值，0=不预警',
  category     VARCHAR(64)                          COMMENT '类目',
  status       VARCHAR(16)  NOT NULL DEFAULT 'draft' COMMENT 'draft/on_shelf/off_shelf',
  cover_url    VARCHAR(512)                         COMMENT '宣传图（主图）',
  sort_no      INT          NOT NULL DEFAULT 0      COMMENT '陈列排序（越小越前）',
  pinned       TINYINT(1)   NOT NULL DEFAULT 0      COMMENT '陈列置顶',
  created_at   DATETIME     NOT NULL,
  updated_at   DATETIME     NOT NULL,
  UNIQUE KEY uk_goods (seller_id, goods_no),
  KEY idx_shelf (seller_id, status, pinned, sort_no),
  KEY idx_low_stock (seller_id, stock)
) COMMENT '商品主表：陈列=status on_shelf 视图，管理=全量视图';

-- 1b. 操作日志（人工与 AI 的动作都记；延续本项目「可审计」基因）
CREATE TABLE operation_log (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  seller_id   VARCHAR(64)  NOT NULL DEFAULT 'default',
  actor       VARCHAR(16)  NOT NULL COMMENT 'human（卖家）/ ai（助手）/ system（系统，如预警）',
  action      VARCHAR(48)  NOT NULL COMMENT '如 update_price / create_goods / delete_goods / bulk_update_price',
  target_type VARCHAR(24)  NOT NULL COMMENT 'goods / case',
  target_id   VARCHAR(64)  NOT NULL,
  summary     VARCHAR(255) NOT NULL COMMENT '人可读的一句话',
  before_json JSON                                  COMMENT '变更前（用于撤销）',
  after_json  JSON                                  COMMENT '变更后',
  undoable    TINYINT(1)   NOT NULL DEFAULT 0       COMMENT '是否可撤销',
  undone_at   DATETIME                              COMMENT '被撤销时刻，NULL=未撤销',
  created_at  DATETIME     NOT NULL,
  KEY idx_target (seller_id, target_type, target_id, created_at),
  KEY idx_actor (seller_id, actor, created_at)
) COMMENT '操作日志：谁在什么时候改了什么，AI 的动作同样留痕';

-- 2. 商品图片（宣传图可多张，首张为主图）
CREATE TABLE goods_media (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  seller_id  VARCHAR(64)  NOT NULL DEFAULT 'default',
  goods_id   BIGINT       NOT NULL,
  url        VARCHAR(512) NOT NULL,
  kind       VARCHAR(16)  NOT NULL DEFAULT 'cover' COMMENT 'cover/detail',
  sort_no    INT          NOT NULL DEFAULT 0,
  created_at DATETIME     NOT NULL,
  KEY idx_goods (goods_id, sort_no)
) COMMENT '商品图片；goods 删除时级联清理';

-- 3. AI 助手消息（与售后对话表分开，避免污染售后审计链）
CREATE TABLE assistant_message (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  seller_id  VARCHAR(64) NOT NULL DEFAULT 'default',
  thread_id  VARCHAR(64) NOT NULL,
  seq        INT         NOT NULL,
  role       VARCHAR(16) NOT NULL COMMENT 'seller/assistant/tool',
  content    TEXT,
  tool_name  VARCHAR(64),
  tool_args  JSON,
  created_at DATETIME    NOT NULL,
  UNIQUE KEY uk_thread_seq (thread_id, seq)
);

-- 4. 待确认的破坏性动作（人在环）
CREATE TABLE pending_action (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  seller_id  VARCHAR(64)  NOT NULL DEFAULT 'default',
  thread_id  VARCHAR(64)  NOT NULL,
  tool_name  VARCHAR(64)  NOT NULL,
  arguments  JSON         NOT NULL,
  summary    VARCHAR(255) NOT NULL COMMENT '给卖家看的一句话说明',
  status     VARCHAR(16)  NOT NULL DEFAULT 'pending' COMMENT 'pending/confirmed/cancelled/expired',
  created_at DATETIME     NOT NULL,
  decided_at DATETIME,
  KEY idx_pending (seller_id, status)
) COMMENT 'AI 提出的破坏性动作，须卖家确认才执行';
```

**商品状态机**：`draft`（草稿）→ `on_shelf`（上架）⇄ `off_shelf`（下架）；删除＝硬删 + 级联删 `goods_media`。
建表脚本：`sql/goods_schema.sql`（与现有 `sql/chat_schema.sql` 并列，**不改现有表**）。

### 鉴权挂载点（用户要求"预留登录接口"）

```python
# app/seller/deps.py
async def require_seller() -> str:
    """返回当前卖家标识。

    现阶段：固定返回 "default"（单卖家、无登录）。
    多卖家迭代时：改为从会话/Token 解析，并在此处做数据隔离——
    所有 /api/seller/* 端点已依赖本函数，替换实现即可，无需改端点。
    """
    return DEFAULT_SELLER_ID
```

**每个 `/api/seller/*` 端点都挂 `Depends(require_seller)`**——这是"预留"的实质：将来只改这一个函数。

## 五、AI 助手（核心新增）

### 工具注册表（第一版）

工具自带元数据，助手据此决定能否直接执行。

| 工具 | 域 | 破坏性 | 说明 |
| --- | --- | --- | --- |
| `list_goods` | goods | 否 | 按状态/关键词查商品 |
| `get_goods` | goods | 否 | 单个商品详情 |
| `create_goods` | goods | 否 | 新建商品（默认 `draft`，不直接上架） |
| `update_goods` | goods | 否 | 改标题/文案/价格/类目 |
| `set_goods_status` | goods | 否 | 上架 / 下架 |
| `delete_goods` | goods | **是** | 删除商品 → **必须确认** |
| `generate_copy` | goods | 否 | 生成/改写文案（计费） |
| `suggest_price` | goods | 否 | 定价建议（计费） |
| `list_aftersale_cases` | aftersale | 否 | 查售后工单 |
| `get_aftersale_case` | aftersale | 否 | 工单详情（复用现有 `console.get_detail`） |
| `resume_aftersale_case` | aftersale | **是** | 退回智能体 → **必须确认** |

### 破坏性动作的在环确认（关键机制）

```
卖家：「把那个手机壳删了」
  ↓
助手：调用 delete_goods(goods_id=12)
  ↓ registry 判定 destructive=true
  ↓ 不执行，写 pending_action（status=pending）+ 返回给模型/界面
界面：弹出确认卡 ——「将删除商品「XX 手机壳」（¥199）及 3 张图片，不可恢复」
  ↓ 卖家点「确认」
POST /api/seller/assistant/actions/{id}/confirm → 真正执行 → 结果回灌对话
```

**为什么必须这样**：模型误判的代价不可逆（商品与图片一起没了）。这与售后里"资金动作必须人工确认"是同一条原则——**自主性在过程，确定性/不可逆动作在人**。

### 上下文注入

请求体带 `context`：

```json
{ "message": "把它的价格改成 99", "context": { "view": "goods_admin", "selected_goods_id": 12 } }
```

拼进 system prompt（"卖家当前在商品管理页，选中商品 #12（XX 手机壳，¥199）"），
避免"你要改哪个"的来回追问——**这是"懂上下文"与"只会聊天"的分界**。

## 六、分阶段实施

### 原型 v2 新增 7 项 → 落在哪个阶段

用户 2026-10-16 要求"基于 v1 原型思考还能加什么"，经评审纳入以下 7 项（原型见
`docs/prototype/seller_console_prototype_v2.html`）：

| # | 新增功能 | 一句话价值 | 归属阶段 |
| --- | --- | --- | --- |
| 1 | **概览看板** | 卖家一进来就知道"今天该处理什么"，不用挨个模块翻 | 一 |
| 2 | **库存与低库存预警** | 卖断货是直接损失；库存是商品管理的刚需字段 | 一 |
| 3 | **批量操作** | 一次处理多件 → 直接兑现"让人投入更小精力" | 一 |
| 4 | **操作日志（含撤销）** | 人工与 **AI 的动作全部留痕、可回滚**——延续本项目「可审计」基因 | 一 |
| 5 | **商品 × 售后联动** | 商品维度的退货率与主要问题，反哺商品优化（业务闭环） | 四 |
| 6 | **陈列编排（排序/置顶）** | "陈列"不只是展示，还要能编排展示顺序 | 一 |
| 7 | **AI 能力面板 + 多步任务** | 让卖家知道"能说什么"；一句话改多件时先出确认卡 | 二 |

> 其中第 4 项是本项目既有优势（可审计决策）在新主线上的自然延伸：
> **AI 替你动手的前提，是它的每一步都能被看见、被撤回。**
> 这也是"AI 助手"能取得信任、而不只是一个玩具的关键。

### 阶段表

| 阶段 | 内容 | 可验收结果 |
| --- | --- | --- |

| **四 · 商品 × 售后联动**（v2 增强 5） | 售后统计聚合（单量/退货率/问题分布）+ 商品详情售后区块 + 工单里点商品可跳转 | 商品详情能看到退货率与主要问题；工单与商品双向可达 |
| **五 · 下一轮** | AI 宣传图生成、多卖家登录与数据隔离、CSV 导入导出 | —— |

**每阶段独立可用**：阶段一做完就是一个能用的卖家控制台（无 AI 也能跑），阶段二开始才是"能动手的助手"。
