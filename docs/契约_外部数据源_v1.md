# 契约 · 外部数据源 v1

> **日期**：2026-10-16 · **状态**：**假设契约**（尚未与真实业务系统核对）
> **地位**：本文是外部接口的**唯一真相**。Mock 按它造数据、HTTP 适配器按它映射、接真实 API 时按它逐字段核对。
> ⚠️ **当前所有字段均为假设**（原代码注释已标注"待与真实接口核对"）。接真机时**必须逐项核对并修正本文**，
> 而不是只改代码——否则文档与实现又成两份真相。

---

## 零、通用约定

| 项 | 约定 |
| --- | --- |
| 协议 | HTTPS，`GET`（只读通道） |
| 编码 | UTF-8，`application/json` |
| 超时 | 默认 3s（`http_client._DEFAULT_TIMEOUT`） |
| 并发 | 全局信号量限流，上限 10 |
| **失败语义** | **未配置 / 超时 / 非 2xx / 解析失败 / 字段非法 → 一律返回 `None`，绝不抛异常** |
| 为什么不上抛 | 取数失败交由规则 R8 判「数据不足 → 转人工」，**网络异常不得中断判定链路** |
| 返回值类型 | 顶层必须是 JSON **对象**（数组/标量视为解析失败） |
| 字段缺失 | 用安全转换（`coerce_*`）回落默认值，**不因单个字段缺失整条丢弃**（`order_id` 除外） |

## 一、订单快照

```
GET {ORDER_API_BASE}/orders/{order_id}
```

| 字段 | 类型 | 必填 | 语义 | 取值 / 默认 |
| --- | --- | --- | --- | --- |
| `item_category` | string | 否 | 商品类目 | 缺失 → `""` |
| `pay_amount` | number | **是** | 实付金额（元） | 缺失/非法 → `0.0` |
| `signed_at` | string(ISO8601) | 否 | 签收时间 | 缺失/非法 → `None` |
| `logistics_status` | string（枚举） | 否 | 物流状态 | `not_signed` / `in_transit` / `signed`；非法 → `in_transit` |
| `goods_no` | string | 否 | **该订单对应的商品编号**（卖家控制台 `goods.goods_no`，如 `G-0001`） | 缺失 → `""`（见下方说明） |

> **关于 `goods_no`（2026-10-16 新增）**：
> 商品是**卖家自建**的、订单来自**外部业务系统**，两者本来毫无关联。
> 没有这个字段，「商品 × 售后联动」就算不出"这个商品退货率多少" ——
> **它是两者之间唯一的桥**。真实业务里应由订单系统提供；本地夹具按约定注入。
> 缺失时售后统计会显示"暂无关联工单"，而不是把数据算到别的商品头上。

**响应示例**

```json
{
  "order_id": "O202610130001",
  "item_category": "日用百货",
  "pay_amount": 39.0,
  "signed_at": "2026-10-10T14:22:00",
  "logistics_status": "signed",
  "goods_no": "G-0001"
}
```

**映射落点**：`adapters/mapping.py: to_order()` → `models.OrderSnapshot`

## 二、物流信息

```
GET {LOGISTICS_API_BASE}/logistics/{order_id}
```

| 字段 | 类型 | 必填 | 语义 | 取值 / 默认 |
| --- | --- | --- | --- | --- |
| `logistics_status` | string（枚举） | 否 | 物流状态 | 同上；非法 → `in_transit` |
| `signed_at` | string(ISO8601) | 否 | 签收时间 | 缺失/非法 → `None` |
| `traces` | string[] | 否 | 物流轨迹（按时间正序） | 缺失 → `[]`；元素强转 string |

**响应示例**

```json
{
  "order_id": "O202610130001",
  "logistics_status": "signed",
  "signed_at": "2026-10-10T14:22:00",
  "traces": ["已揽收", "到达派送点", "已签收"]
}
```

**映射落点**：`adapters/mapping.py: to_logistics()` → `models.LogisticsInfo`

## 三、买家画像

```
GET {AFTERSALE_API_BASE}/profiles/{order_id}
```

> ⚠️ **本接口借用了 `AFTERSALE_API_BASE`**（历史遗留，画像与售后共用同一 base）。
> 接真机时建议独立为 `PROFILE_API_BASE`；届时需同步改契约与 `.env`。

| 字段 | 类型 | 必填 | 语义 | 取值 / 默认 |
| --- | --- | --- | --- | --- |
| `buyer_id` | string | 否 | 买家标识 | 缺失 → `""`（M1 当前以 `order_id` 为查询键） |
| `buyer_credit_score` | integer | 否 | 买家信用分 | 缺失/非法 → **`600`**（规则 R4 门槛 650） |
| `buyer_refund_rate_90d` | number | 否 | 近 90 天退款率 | `0.0 ~ 1.0`；非法 → `0.0`（R4/R5 门槛 0.20） |
| `refund_count_90d` | integer | 否 | 近 90 天退款笔数 | 缺失/非法 → `0`（R5 门槛 6） |

**响应示例**

```json
{
  "buyer_credit_score": 700,
  "buyer_refund_rate_90d": 0.05,
  "refund_count_90d": 1
}
```

**映射落点**：`adapters/mapping.py: to_profile()` → `models.BuyerProfile`

## 四、处置执行（**写通道，语义与上三者根本不同**）

```
POST {DISPOSAL_API_BASE}/disposals
Header: Idempotency-Key: {request_id}
Body:   { "action": "refund", "request_id": "...", "order_id": "...", "amount": 89.0 }
```

| 字段 | 类型 | 语义 |
| --- | --- | --- |
| `status` | string | 受理状态；**仅** `ok` / `accepted` / `success` / `succeeded` 视为受理 |
| `disposal_id` | string | 处置单号（审计留痕用） |

| 与读通道的差异 | 读通道 | 写通道 |
| --- | --- | --- |
| 失败处理 | 返回 `None`，交由规则判"数据不足" | **绝不可当成功**；显式失败并**升级人工** |
| 未配置时 | 回落本地夹具（开发用） | **拒绝执行**（绝不 mock 成功） |
| 幂等 | 不需要 | **必须**：`Idempotency-Key` 防重复退款 |
| 限流 | 共用信号量（上限 10） | **独立信号量**（上限 3），避免与取数抢配额 |

> ⚠️ **写通道不纳入可插拔端口**（见 `设计_可插拔适配层_v1.md`）：
> 它的"未配置即拒绝"与读通道的"未配置即降级"语义**根本相反**，
> 混进同一个 `DataSource` 端口会污染语义。本契约只登记其接口形态，实现保持现状。
