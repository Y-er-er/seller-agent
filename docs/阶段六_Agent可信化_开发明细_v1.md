# 阶段六 · Agent 可信化 —— 开发明细 v1

> 状态：**待确认**（用户确认后再开工）
> 前置：阶段一~五已完成；当前 AI 具备 16 个工具、破坏性/计费动作走确认卡。
> 本阶段**不新增业务功能**，目标是把 Agent 从"能动手"推到"**可托付**"。

---

## 一、阶段目标

一句话：**让 AI 能代替人做完该做的事，且做错了能自己收拾。**

对照当前的两个硬缺口（均有实证）：

| 缺口 | 证据 |
| --- | --- |
| ① **能力不对等**：人能做的，AI 做不全 | `list_goods` 只有 `keyword/status/low_stock`，而界面已有类目/价格区间/库存区间/排序；另有 4 个已有端点未注册成工具（商品售后统计 / 任务 / 日志 / 撤销） |
| ② **失败不可控**：无重试、无回滚 | 全项目无 `retry`；批量"成功 3 失败 2"不回滚；多步任务中途失败，前面已完成的改动不会撤销 |

## 二、范围

### 做

- **A 能力对齐**：AI 能做的事 = 人能做的事
- **B 失败可控**：补偿（回滚）、重试、降级策略
- **C 删除可恢复**：回收站（7 天，到期彻底删除）

### 不做（明确边界）

| 不做 | 原因 |
| --- | --- |
| 主动巡检（L3） | 它是**新能力**，不是修缺口；放阶段七单独做 |
| 对接真实平台 API | 先证明"在自己的世界里能代替人做完所有事"，再出去碰真实世界 |
| SPU/SKU 数据模型 | 数据模型级改动，与"接真实业务"绑定，单独成阶段 |
| 多卖家登录 | ✅ 已单独完成（2026-10-20，见方案文档「登录与鉴权」）；本阶段仍不含自助注册 |
| 创建时间筛选 | 需先确认 `goods` 是否带 `created_at`，不做半截功能 |

## 三、明细

### A. 能力对齐

#### A1 · 补齐 4 个工具（新建 `app/assistant/tools_ops.py`）

| 工具 | 参数 | 实现 | 域 |
| --- | --- | --- | --- |
| `get_goods_aftersale` | `goods_no` | 复用 `app/goods/aftersale_stats.stats_for_goods` | goods |
| `list_tasks` | `status?` `limit?` | 复用 `app/db/task_repo.list_tasks` | ops（新域） |
| `list_logs` | `actor?` `target_id?` `limit?` | 复用 `goods_repo.list_logs` | ops |
| `undo_log` | `log_id` | 复用 `goods_service.undo` | ops |

- **`ops` 为新增域**（任务 / 日志 / 撤销），能力面板自动多一组「运维」。
- `undo_log` 标 **`destructive=True`**：它改数据，且撤销本身可能被误解为"无害"——必须让卖家看见。
- 验收：
  - `/capabilities` 出现「运维」分组；
  - 助手能回答"G-0001 退货率多少""我的图生成好没有""我上一步干了什么"；
  - 4 个工具均有单测（假仓储）。

#### A2 · `list_goods` 扩展筛选（与界面完全对齐）

新增参数：`category` / `price_min` / `price_max` / `stock_min` / `stock_max` / `sort`（`price|stock|updated_at`）/ `order`（`asc|desc`）

- 需同步改 `app/db/goods_repo.list_goods`（现在只支持 `q/status/low_stock`）。
- **口径必须与前端一致**：`low_stock` = `stock_alert > 0 且 stock <= stock_alert`；价格/库存区间为闭区间。
- 验收：
  - AI 能完成"找 100 元以下、库存紧张的数码配件"；
  - 同一组条件，AI 结果与界面筛选结果**逐条一致**（用同一份数据对照测试）。

#### A3 · 工具覆盖自动比对测试（新建 `tests/test_tool_coverage.py`）

遍历 `app.openapi()['paths']`，对照 `registry.all_specs()`：

- 每个"卖家可执行的业务动作端点"必须有同名工具；
- 白名单豁免纯 UI 端点：`/uploads/*`、`/overview`、`/capabilities`、`/goods/{id}/media`（图片走上传交互）。
- 验收：故意删掉一个工具 → 测试**失败**并指名缺哪个。

> 这条是为了**永久堵住"端点做了、工具忘了"**——同类问题已发生三次（生图、文案定价、4 个盲区）。

### B. 失败可控

#### B1 · 多步任务事务（补偿）—— ⚠️ **执行时调整为推迟（2026-10-19）**

> **调整说明**：原计划"一轮任务失败就逆序回滚"**没有落地**，原因不是难，而是**语义不对**：
> 当前每个工具都是**原子操作**（"改价"和"上架"是卖家要求的两件独立的事）。
> 若"上架失败就回滚刚才的改价"，等于**撤掉卖家明确要求过的动作**，反而更糟。
> 事务补偿真正需要的是"**一个业务动作包含多个原子步骤**"（如"上架 = 校验 + 改状态 + 重排陈列"），
> 当前没有这种场景 —— **不为做而做**。
>
> **替代方案（已实现）**：**B1' 同轮重复调用拦截** —— 直接堵住"重复执行、重复计费"
> （这是实测中真实发生的病灶）。见下方 B1'。

**原设计（保留备查）**：一个"任务"可包含多个动作；执行前记录 `before` 快照，失败时**逆序撤销**已成功项。

- 复用现有 `operation_log.before/after`（已有 undo 能力，不新建表）。
- 新增 `app/goods/tx.py`：`run_steps(steps, *, stop_on_error=True)` →
  逐条执行，成功记快照；失败按逆序回滚，返回 `{done, rolled_back, failed_at}`。
- **边界（必须写进代码注释）**：
  - 补偿只覆盖**本任务内、且 `undoable=True`** 的动作；
  - **删除**（不可逆）不参与补偿 → 若任务含删除，删除必须是**最后一步**；
  - 跨"确认卡"的任务**不跨段补偿**（确认前的不回滚）。
- 验收：
  - 构造"改价成功 → 上架失败" → 价格必须回到原值；
  - 构造"改价 → 删除 → 上架失败" → **拒绝执行**（删除不在最后），并明确报错。

#### B1' · 同轮重复调用拦截（**已实现**，替代 B1）

**机制**：`_dispatch` 维护本轮 `seen` 集合（`工具名 + 规范化参数`）。
同轮内**重复的有副作用调用**（`needs_confirm`）→ **不执行**，回灌：

> 这个操作在本轮**已经执行过一次**，结果见上文。**不要重复调用** —— 重复执行会重复生效、重复计费。

- 只拦**有副作用**的（不可逆/计费）；只读重复无害，甚至可能是模型在核对。
- 验收：同轮连续两次 `generate_cover(同一商品)` → **只建 1 张卡**；trace 标注"重复调用已拦截"。

#### B2' · 重试（**已实现**）

- `app/assistant/loop.py` 的工具执行处：命中白名单且为**瞬时错误**（超时/连接重置/5xx）→ 自动重试 1 次。
- **白名单只含读与幂等写**：`list_*` / `get_*` / `set_goods_status`（幂等）/ `update_goods`（同值幂等）。
- **绝不重试**：`delete_goods` / `bulk_apply` / `undo_log` / `resume|close_aftersale_case` / 全部计费工具
  （重试 = 重复计费）。
- 验收：桩注入一次超时 → 第二次成功且只记录 1 次操作日志；`delete_goods` 超时 → **不重试**，直接报错。

#### B3 · 降级矩阵（统一策略）

`registry.ToolSpec` 增加 `failure_policy`：`retryable | degrade | fail_fast`，并在 `docs/` 写一张矩阵表。

| 类型 | 策略 | 例子 |
| --- | --- | --- |
| 读 | retryable | `list_goods`、`get_goods` |
| AI 生成 | degrade（已有回落） | 生图 prompt → 模板；定价 → 规则估算 |
| 写 | fail_fast（不降级） | `update_goods`、`set_goods_status` |
| 不可逆 / 计费 | fail_fast + 人工确认 | `delete_goods`、`generate_cover` |

- 验收：注册表能自检——`failure_policy` 与 `destructive/billable` 冲突时**注册期报错**
  （如删除被标成 `retryable`）。

#### B4 · 步数上限 6 → 12

- `MAX_STEPS = 12`，`DEFAULT_TOOL_BUDGET` 保持 8（预算仍按"实际工具调用"卡，不按往返次数）。
- 验收：构造 8 步任务能完成；构造死循环仍被 12 步截断。

### C. 删除可恢复（回收站）

#### C1 · 数据模型

`sql/migrations/2026-10-19_add_goods_deleted.sql`（幂等）：

- `goods` 增加 `deleted_at DATETIME NULL` + `KEY idx_deleted (deleted_at)`；
- 软删 = `status='deleted'` + `deleted_at=NOW()`；**不再物理删除**。

#### C2 · 全链路排除

所有"正常视图"必须排除 `deleted_at IS NOT NULL`：

- `goods_repo.list_goods` / `get_goods`（get 需区分"不存在"与"在回收站"）
- 陈列 `list_gallery`、概览统计 `overview`、低库存筛选
- `aftersale_stats`（商品维度统计）
- **验收**：删除后，列表/陈列/概览/低库存/售后统计 **五处全部消失**。

#### C3 · 回收站 API

- `GET /api/seller/goods/trash`（列表，含"剩余 N 天"）
- `POST /api/seller/goods/{id}/restore`（恢复）
- `DELETE /api/seller/goods/{id}/purge?confirm=true`（彻底删除：商品 + 图片 + media 行）
- 彻底删除需 `confirm=true`（与现有删除同规矩）。

#### C4 · 到期清理

- 配置 `GOODS_TRASH_DAYS=7`（0 = 不自动清）。
- 时机：**服务启动时** + **每次打开回收站时**（不引入定时任务框架）。
- 到期：物理删除 + 图片 + media 行，记 `system` 日志。
- 验收：把 `deleted_at` 改成 8 天前 → 打开回收站后该商品**已不存在**。

#### C5 · AI 联动

- `delete_goods` 改为软删；确认卡文案：**「删除商品（移入回收站，7 天内可恢复）」**；
- 仍标 `destructive=True`（列表消失、买家看不到，仍是重大变更，只是话术变了）。

#### C6 · 前端

- 商品管理第三个 tab：`[全部商品 N] [低库存 N] [回收站 N]`；
- 回收站列表：每行「剩余 N 天」+ 恢复 / 彻底删除；顶部提示条 + 「清空回收站」；
- 批量删除的 diff 提示改为「移入回收站」。

## 四、执行顺序与分批

| 批 | 内容 | 复杂度 | 可独立验收 |
| --- | --- | --- | --- |
| 1 | A1 + A2 + A3 | 中 | ✅ 工具覆盖测试绿 = 能力对齐完成 |
| 2 | C1~C6 | 中 | ✅ 五处消失 + 恢复/彻底删除跑通 |
| 3 | B1 + B2 + B3 + B4 | 高 | ✅ 事务回滚、重试白名单、降级矩阵自检 |

**为什么这个顺序**：A 风险最低且直接补缺口 → C 是已承诺的功能 → B 要动循环核心，放最后且单独验证。

## 六、风险与回滚

| 风险 | 缓解 |
| --- | --- |
| C 影响面大（所有查询都要排除已删） | 先写"五处全消失"的测试，再改实现 |

| 改坏数据 | 动手前 `mysqldump` 备份 `goods` / `goods_media` / `operation_log` |

## 七、本阶段验收清单（AI 代替手动 · 10 条）

逐条实测（需真实模型），全部通过才算完成：

1. 「我有哪些商品」→ 列出，含价格/状态/库存
2. 「找 100 元以下、库存紧张的数码配件」→ 与界面筛选结果一致
3. 「G-0001 价格改成 89」→ 改完成，陈列同步
4. 「把 G-0001 上架」→ 状态变化
5. 「批量把这几件改价 -10」→ 逐件 diff → 确认 → 成功/失败明细
6. 「G-0001 的退货率多少」→ 报统计（含样本量）
7. 「我的宣传图生成好了吗」→ 报任务进度
8. 「刚才那步改价撤销掉」→ 撤销成功且留痕
9. 「给 G-0001 生成宣传图和文案，然后上架」→ **多步任务能跑完**（确认卡后继续）
10. 「删掉 G-0001」→ 确认卡提示"可恢复" → 进回收站 → 恢复成功

> 第 9 条是 B 的存在意义；第 10 条是 C 的存在意义。
