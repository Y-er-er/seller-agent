# 商铺经营Agent · 启动与自测指南

> 本文档说明如何在**本机**启动项目并自测。
> 模型按正常业务使用（`.env` 默认 `LLM_ENABLED=true`）：对话、问答润色、视觉理解三类请求
> 都会产生**真实计费调用**。资金动作默认仍是影子模式（不产生真实退款/补发）。

## 二、启动后端

> **订单与客服新增表（2026-10-21）**：使用这两个新模块前，需先在目标 MySQL 库执行
> `sql/order_schema.sql` 与 `sql/service_schema.sql`。应用不会自动执行这两份迁移；
> 尚未迁移时新接口返回 503。执行迁移前先确认目标库与备份，参见
> `docs/方案_订单与客服会话_v1.md`。其余旧模块可照原流程启动。

在 `backend/` 目录下执行：

```bash
cd E:/PycharmProject/agent_shop/Shop-Agent/backend
D:/Anaconda1/envs/pythonproject/python.exe run.py
```

等价于：

```bash
D:/Anaconda1/envs/pythonproject/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

- `run.py` 默认设 `CHAT_ENABLED=true`（对话入口：指挥台 + 买家 H5）。关闭则相关端点返回 503。
- 启动时自动注入 `config/demo_orders.yaml` 中的假订单；此外买家界面的**「演示模式」开关**
  可按任意订单号即时合成夹具（见《定位与最小闭环_v1》§七）。
- **单价（`PRICE_*_PER_1K`）不是启动前置项**：留空时成本闸门只按 token 计量，不影响正常运行，
  也不会产生任何启动告警。
- 若只想验证规则链路与前端、不调用模型，可临时覆盖开关：

  ```bash
  LLM_ENABLED=false D:/Anaconda1/envs/pythonproject/python.exe run.py
  ```

  此时对话会走"模型不可用 → 转人工"降级路径，链路仍通，但不是自主决策。

### PyCharm 里跑（推荐用便捷脚本）

> ⚠️ **不要直接 Run `app/main.py`**。它用的是**包内导入**（`from app import ...`）且**没有启动入口块**
> （只有 `app = FastAPI(...)`）。直接运行会报 `ModuleNotFoundError: No module named 'app'`，
> 且即使导入成功也不会起服务（跑完就退出）。**这不是故障，是 FastAPI/ASGI 的标准形态**——
> 服务必须由 ASGI 服务器（uvicorn）加载启动。

**做法①（最简单）**：右键 Run `backend/run.py`（仓库自带的便捷启动脚本），它已默认 `CHAT_ENABLED=true`。

**做法②（标准）**：配一个 PyCharm Run Configuration：

| 字段 | 值 |
| --- | --- |
| 入口 | Run → Edit Configurations → `+` → **Python** |
| Name | 售后智能体后端 |
| **运行方式** | 选 **module**（不是 script），填 `uvicorn` |
| Parameters | `app.main:app --host 127.0.0.1 --port 8000` |
| Working directory | `…/Shop-Agent/backend` |
| Environment variables | `CHAT_ENABLED=true` |
| Interpreter | conda `pythonproject` |

## 三之二、商铺经营Agent登录（浮窗式，不跳页面）

打开 `seller.html` 后会**先弹一个登录浮窗**（浮动在控制台上，地址栏不变）。
登录成功后浮窗关闭、原地加载数据，不会跳到另一个页面。

**首次启动自动创建初始账号**（仅在账号表为空时）：`admin` / `admin123`，
显示名与业务数据归属由 `.env` 决定：

```ini
SELLER_BOOTSTRAP_USERNAME=admin
SELLER_BOOTSTRAP_PASSWORD=admin123      # ← 上线前务必改掉
SELLER_BOOTSTRAP_NAME=默认卖家
SELLER_BOOTSTRAP_SELLER_ID=default      # default = 现有的演示店铺数据
SELLER_SESSION_HOURS=12                 # 会话有效期（小时）
```

> ⚠️ **改 `.env` 里的密码对已存在的账号无效** —— 那段只在"账号表为空"时生效。
> 改已有账号的密码：
> ```bash
> cd backend
> python scripts/create_seller_account.py --username admin --password '新口令' --reset-password
> ```

**新建一个卖家账号**（会是一间**空店**：没有商品、没有知识库 —— 这是数据隔离的事实）：

```bash
python scripts/create_seller_account.py --username alice --password '强口令' \
    --display-name 爱丽丝 --seller-id shop_alice
```

想看演示商品，请用绑定 `default` 的账号（默认就是 `admin`）。

**几条行为要知道**：

| 行为 | 说明 |
| --- | --- |
| 每次登录都是新对话 | 后端给每次登录分配**新的助手线程**；上一段对话不会消失（留在库里），但不会再出现在界面上 |
| 会话过期 | 12 小时后任何请求返回 401 → 界面**就地再弹登录浮窗**（有 Token 时会提示"登录已失效"） |
| 退出登录 | 左栏底部「退出登录」；服务端**立即失效**，不是等过期 |
| 连续输错 | 同账号 5 次失败锁 10 分钟（计数在进程内，重启即清零） |
| 数据表 | `sql/seller_schema.sql`（`seller_account` / `seller_session`）；后端启动会自动建表，无需手跑 |

## 四、模型配置（出问题先看这一节）

### ⚠️ 文本模型必须是「纯文本模型」

`app/chat/llm_adapter.py` 经由 langchain 的 `ChatTongyi` 调用模型，而它**只按模型名里是否含 `vl`
推断调用端点**：含 `vl` → 多模态端点 `multimodal-generation`，否则 → 纯文本端点 `text-generation`。
这个判据认不出新出的多模态模型（名字里没有 `vl`），会把它们误判到纯文本端点，服务端随即返回：

```
400 InvalidParameter: url error, please check url!
```

**典型症状**：买家发一条消息，智能体回「抱歉，我这边刚刚出了点问题，请再说一次。」
（`model_error` 降级话术），终端打印上面这条 `模型调用失败`。

| 项 | 取值 | 说明 |
| --- | --- | --- |
| `LLM_TEXT_MODEL` | `qwen3.7-max` | 官方明确标注的**纯文本**模型，支持 Function Calling |
| `LLM_VISION_MODEL` | `qwen3-vl-plus` | 多模态；由 `app/llm/client.py` 直接调 `MultiModalConversation`，端点匹配 |

**已知不可用作文本模型的型号**（名字不含 `vl` 但实际是多模态）：
`qwen3.7-plus`、`qwen3.8-max`、`qwen3.8-flash`。
`config_validation` 会在启动期对这三个型号直接点名告警——见到该告警就换模型名。

### 为什么控制台把它标成「大语言模型」？

百炼控制台「免费额度 / 模型广场」里的**「模型类型」是产品与计费维度，不决定 API 走哪个端点**。
`qwen3.7-plus` 的官方描述是"在文本能力基础上全面升级了视觉-语言能力"的混合模型，控制台按
「大语言模型」归类（它不是纯视觉模型），但 **API 侧要求走 `multimodal-generation` 端点**。

需要知道的是，**官方文档自身对这个型号的口径也不统一**：

| 官方来源 | 对 `qwen3.7-plus` 的归类 |
| --- | --- |
| 百炼控制台「模型类型」字段 | 大语言模型 |
| 官方错误码页（中文） | **多模态模型**（明确要求 `MultiModalConversation`） |
| 官方错误码页（英文） | "多模态模型"与"文本模型"两处**都列了它**（自相矛盾） |

**结论：以错误码页给出的端点要求为准**（它是按"调用失败"倒推的，最贴近实际行为）；
控制台的类型标签只作参考。判断某型号能否直接走文本通道，可靠办法是实测一次，
或查它在「图像与视频理解」文档里是否出现。

> 参考：<https://help.aliyun.com/zh/model-studio/error-code>（`url error` 原因一）

### 换模型后成本闸门还在拦？（2026-10-20 已修）

**现象**：把 `LLM_TEXT_MODEL` 换成另一个型号，助手仍每轮回
「已用 token NNN 已达免费额度 …，已暂停新会话」，点「继续」也是同一句。

**原因**：免费额度是**按模型各发一份**的，但旧实现把 `llm_usage` **全表求和**再跟
`FREE_QUOTA_TOKENS` 比 —— 于是旧模型的已用量被新模型"继承"了。
实测过的一组数字：`qwen3.7-max` 用了 60.7 万、`qwen3.7-max-preview` 用了 39.5 万，
合计 100.2 万 ≥ 100 万，新模型明明还剩 60 万却被判耗尽。

**现口径**（`app/chat/cost_gate.py`）：

| 判定 | 用什么数 | 为什么 |
| --- | --- | --- |
| 免费额度耗尽 | **当前 `LLM_TEXT_MODEL` 的累计** + `FREE_QUOTA_USED_BASELINE` | 额度按模型发放，各算各的 |
| 月度预警 / 硬上限 | **全部模型**本月合计 | 那是"这个月一共花了多少钱" |

所以 `FREE_QUOTA_TOKENS` 是**单个模型**的额度，**换模型不用改它**；
`FREE_QUOTA_USED_BASELINE` 填的是"该模型在控制台上、本项目之外"的已用量。

**自查**：`/api/health` 的闸门状态里 `model` / `model_tokens` 是判定依据，
`total_tokens` 只是展示用的全模型累计——别拿后者去比免费额度。

## 八、常见问题

| 现象 | 原因 / 处理 |
| --- | --- |
| 智能体回「**抱歉，我这边刚刚出了点问题，请再说一次。**」 | **模型调用失败**（`model_error`）。看终端那行 `模型调用失败：…`：<br>`code: InvalidParameter / url error` → 文本模型名配错（见 §四）；`401 / InvalidApiKey` → 密钥问题；`Timeout / ConnectionError` → 网络 |
| 建单返回 **500** / 会话创建失败 | **MySQL 不可达**——检查 VM 与 Docker 是否启动 |
| 端点返回 **503**「对话入口当前未启用」 | 启动时没加 `CHAT_ENABLED=true` |
| 页面显示「**后端不可达**」 | 后端没启动，或端口不是 8000（用 `?api=` 覆盖） |
| 指挥台工单「**已转人工**」但处理者是 `—` 或「智能体」 | 历史数据（早期版本转人工未同时置 `assignee`）。点**接管**即可让归属名实相符；或直接发一条人工消息（发送即接管） |
| 工单卡在「已转人工」无法推进 | 早期版本无出口。现在有三个动作：**接管**（自己处理）／**退回智能体**（故障排除后交回，`buyer_request` 时不可用）／**人工结案** |
| 日志出现 `创建会话失败（已降级）：Duplicate entry …` | **正常**——`case_id = order_id` 的幂等：该会话已存在，直接复用 |
| 改了后端代码但行为没变 | 进程未重启。`reload=False`，**必须重启** |

## 九、开关速查（backend/.env）

| 开关 | 当前值 | 作用 |
| --- | --- | --- |
| `LLM_ENABLED` | `true` | 模型调用总开关（关则对话走"模型不可用→转人工"降级） |
| `CHAT_ENABLED` | `true`（`run.py` 默认注入） | 对话入口（指挥台 + H5）总开关 |
| `QA_LLM_POLISH` | `true` | 口径问答用模型润色措辞（关则走确定性解释） |
| `VISION_MAX_IMAGES` | `5` | 单笔举证送模型的最大图片数 |
| `SHADOW_MODE` | `true` | **资金安全闸门**：处置只记录不执行 |
| `DISPOSAL_ENABLED` | `false` | **资金安全闸门**：真实执行处置（需与影子模式配合） |
| `VISION_INCLUDE_BUYER_NOTE` | `false` | **合规控制**：买家留言不送第三方模型（个人信息出境） |
| `KNOWLEDGE_ENABLED` | `true` | 知识库总开关（关则助手明确回"知识库已关闭"，**不假装成没查到**） |
| `EMBEDDING_MODEL` / `EMBEDDING_DIMENSIONS` | `text-embedding-v3` / `1024` | 向量化模型与维度。**改维度或换模型必须重建库**，否则旧向量与查询向量不在同一空间 |
| `KNOWLEDGE_TOP_K` | `5` | 默认检索条数（**不设相似度阈值**：连相关度一起给模型看） |
| `KNOWLEDGE_CHUNK_SIZE` / `KNOWLEDGE_CHUNK_OVERLAP` | `700` / `100` | 分块大小与重叠。只在**上传时**生效 —— 改了只影响之后传的资料，旧资料要重传 |
| `KNOWLEDGE_MAX_UPLOAD_BYTES` | `10485760` | 单份资料上限 10 MB（超限在解析前拒绝，不截断） |
| `KNOWLEDGE_DIR` / `KNOWLEDGE_COLLECTION` | `./data/knowledge` / `seller_knowledge` | Chroma 持久化目录与集合名。**删库＝删整个目录**，不要手工删单个文件 |
| `REFUND_WINDOW_DAYS` | `15` | 售后时效（R11 超时效拒绝） |

> 知识库的**密钥不单独配**：向量化复用 `DASHSCOPE_API_KEY`（走 `DASHSCOPE_COMPAT_BASE` 的
> OpenAI 兼容端点），图片 OCR 复用「视觉理解」那条通路（`LLM_VISION_MODEL` + `VISION_TIMEOUT`）。
> OCR 与向量化**都会计费**，属正常模型调用（成本是配置项，不是设计前提）。
