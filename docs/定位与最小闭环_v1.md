## 一、定位声明（冻结）

**一句话**：

> 一个被管理员指派到具体售后事件的处置智能体：**与买家多轮对话、理解诉求、自主决定下一步做什么，循环往复直至给出结论**（退款 / 补发 / 驳回 / 需补证 / 转人工）；管理员全程可见，并可**随时接管、以人工身份直接与买家对话**。

**原始表述**（用户 2026-10-15 给定，保留原文以免二次转述失真）：

> 这个智能体被管理员派给一个售后事件时，能与买家进行对话沟通、理解其诉求、思考自主选择下一步怎么做，循环对话直至能得出结论（是退款、补货、驳回不合理诉求、查询对应信息等一系列），管理员可以随时接入智能体与买家的对话以及作为人工与买家对话。

**与旧表述的差异**（这三处差异是本项目此前的口径漏洞）：

| 维度 | 旧口径 | 新定位 |
| - | - | - |
| 范围 | 仅退款资格判定 | 售后处置全流程（退款 / 补发 / 驳回 / 补证 / 转人工） |
| 主动权 | 智能体单向处理 | 智能体自主循环，**管理员可随时接管** |
| 人工角色 | 兜底（出问题才转人工） | **并行的参与者**——可随时接入、可直接对买家发言 |

## 二、意义与价值主张

**原始表述**（用户 2026-10-15 给定）：

> 制作这个智能体的意义是对接业务，让传统业务变得简单易操作，让人可以投入更小的精力。

**落到本项目，这句话具体兑现为五条机制**：

| # | 机制 | 替代掉的人工动作 |
| - | - | - |
| 1 | 信息汇集自动化（取数工具） | 人工逐个系统翻订单、查物流、看历史 |
| 2 | 判断规则化（R1—R11 规则引擎） | 人工记规则、凭经验判断"该不该赔、赔多少" |
| 3 | 沟通自动化（多轮对话） | 人工反复问同样的问题、反复解释同样的话 |
| 4 | 留痕自动化（审计旁路） | 人工填单、补记录、事后对不上账 |
| 5 | 例外才升级（人在环） | 人工处理**每一单**，包括大量无争议的标准单 |

**结果：人工触点从"处理每一单"收敛到两个动作**——**指派** 与 **确认（或接管）**。

> ⚠️ **一处必须点破的张力**
>
> "让传统业务变简单、让人投入更小精力"是**产品档位**的话语。它的常规验收指标是效率数字——人工介入率、响应时长、处理时长、单位人力处理量。
>
> **这些指标必须有真实业务与数据源才能测量，而本项目恰好没有。** 若直接拿它当作品的验收标准，就会重演此前诊断出的偏离根源：**用不可验证的东西衡量自己**。
>
> **调和方式**：在作品档位下，把"减少精力投入"**转译成可演示的流程对比**，而不是结果指标——
>
> - 不主张："人工介入率下降 40%"（测不了，且无凭据）
> - 而展示："**同一件事情，传统流程需要人工操作 6 处，接入智能体后人工只剩 2 处**"（可当场演示、可复现、不依赖真实数据）
>
> 结论：**意义不变，衡量方式换掉。**这一条写进 §五 的演示脚本，不新增验收条目。

**意义成立的前提**（为什么是售后处置这个方向）：

"让业务变简单"只在**业务本身是标准化的**时候成立——有明确输入、有可枚举的结论、有书面的规则。售后处置恰好满足：诉求可分类、结论可枚举（退款/补发/驳回/补证/转人工）、规则可写成表。反过来说，规则写不成表的场景（创意、谈判、纠纷定性）不适合交给本智能体——那是 §六 边界声明要排除的部分。

## 四、缺口的实施记录

> **状态：四条全部已实施并通过验收（2026-10-15）。**
> 下面先记「问题原状」，再记「实施内容」。保留原状是为了让后来者看清**为什么**这样改——
> 它们**不是待办**。

### 缺口 1 · 人工接管不阻断智能体（阻断性）

**现状**：`console.intervene()` 只改工单维度（`workflow_status=escalated`、`assignee=manual`、记一条 guardrail），**对话通路完全没有感知它**。

`orchestrator.handle_buyer_message()` 的入口守卫只有四条——终态 / 成本闸门 / 字数 / 轮数（`session.append_buyer_message`），**不检查 `workflow_status`，也不检查 `assignee`**。

**后果**：管理员点了「介入」之后，买家再发一条消息，**智能体照常自动回复**。也就是说"接管"在代码上是假的——它只换了工单标签，没换对话的控制权。

**应做**：在 `handle_buyer_message()` 入口增加**接管守卫**——若工单已转人工（`assignee=manual`），不再触发 agentic 循环，改为：消息只落库、进人工待办、给买家回一条"已由人工接待"。

**已实施**：`handle_buyer_message()` 入口**先读工单**判定接管，命中则直接返回
`kind="human_takeover"`，**不触发 agentic 循环**。买家消息仍落库（人工必须看得到）；
买家侧提示走返回字段 `notice`，**不写进会话**（会话此刻归人工，写进去会与人的发言打架）。

**实施中发现并修掉的连带缺陷**：转人工会把会话置为终态 `ESCALATED`，而终态守卫
**会把买家挡在门外**（回"本次会话已结束"）——人反而接不上话，与"随时接入"直接矛盾。
故新增豁免：`state.check_can_accept_message(human_takeover=True)` 时，**终态 / 成本 / 轮数
三条守卫整体不适用**；接管期间的买家消息也**不消耗轮次**（轮次是"买家 ↔ 智能体"的往返计数）。

**验收**：`test_agent.py` A12（6 项）、A15（4 项，含"无人接管时终态仍拒收"的反向断言）。

### 缺口 2 · 没有「人工发消息」这条通道（功能性）

**现状**：会话消息的角色只有 `buyer` / `agent` 两种（`orchestrator._ROLE_TO_MODEL` 仅映射这两个）。**不存在任何让管理员以人工身份写消息的 API**。指挥台有收件箱、指派、介入、确认、驳回五种动作，唯独没有"说话"。

**应做**：

1. 新增角色 `human`，消息表与落库路径支持它；
2. 新增 `POST /api/console/cases/{case_id}/messages`；
3. 人工消息**不经模型改写**直接送达买家（红线：人工的意志不得被模型复述）；
4. 人工消息需进入模型上下文（让智能体"看见"人已经说过什么），避免人机发言打架。

**已实施**：新增会话角色 `human`（`state.ROLE_HUMAN`）；新增 `console.post_human_message()`
与 `POST /api/console/cases/{case_id}/messages`。语义三条——**首次发言即接管**（同时置
`assignee=manual`）、正文**原样落库不经模型改写**、落一条 `human_replied` 护栏事件。
装配模型上下文时映射为 `assistant` 并加 `[人工客服]` 前缀（`orchestrator.HUMAN_PREFIX`），
**只作用于送入模型的历史，不改落库原文**。人工发言**不消耗轮次**。
前端：指挥台新增人工发言区（`console.js::renderComposer`），指挥台与 H5 均按
buyer / agent / human 三种角色分别呈现。

**验收**：`test_console.py` C9—C11；`test_agent.py` A13；`verify_console.cjs`（四角色渲染 + composer）。

### 缺口 3 · 诉求方向未接线 → 补发不可达（正确性）

已在 `slots.py` / `disposal.py` / `models.py` / `orchestrator.py` 逐行核实，三处错配叠加：

| 环节 | 字段名 | 实际值域 |
| - | - | - |
| 模型槽位 | `claim_type` | 中文，实为**原因**：未收到货 / 质量问题 / 错发漏发 / 无理由 / 其他 |
| 模型槽位 | `expectation` | 中文**诉求方向**：仅退款 / 补发 / 换货 / 其他 |
| 领域模型 | `ClaimType` | 英文**诉求方向**：refund / return_refund / reship / exchange / partial_refund |
| `orchestrator.py:221` | `intent` | **硬编码 `"refund"`** |

后果：`assemble_request()` 从不写 `RefundRequest.claim_type`（恒为默认 `REFUND`）、`EXPECTATIONS` 全项目无人消费、两套值域中英不通 → `resolve_disposal()` 永远只能输出 `refund` / `reject` / `manual` / `pending_evidence`，**`reship` 不可达**；R9/R10 补发规则存在但永不命中。

**应做**：术语三分并破坏性改名——`issue_reason`（为什么）/ `issue_object`（问题在哪）/ `claim_direction`（想要什么）；`claim_direction` **必填且禁止默认值**；`resolve_disposal()` 的键值域与 `claim_direction` 统一。

**已实施**：破坏性改名落地——槽位 `claim_type`→`issue_reason`（值实为原因）、
`expectation`→`claim_direction`（值实为诉求方向）；新增 `slots.direction_to_claim_type()`
把中文方向翻译为 `ClaimType`（值域与 `_PASS_BY_CLAIM_TYPE` 对齐，这是此前"映射静默落空"的成因）；
`assemble_request()` 接收 `claim_direction` 并写入 `RefundRequest.claim_type`；
`orchestrator` 中硬编码的 `intent = "refund"` 改为从槽位读取。
连带同步：`tool_spec` 工具参数名与枚举、系统提示词（去掉「仅退款」预设）、
`reply.SLOT_LABELS`、`reply.CONCLUSION_LABELS`（措辞不再绑定"仅退款"）、DDL 注释、前端槽位标签。

**验收**：`test_slots.py` T7（6 项）、`test_agent.py` A14（`claim_direction=补发` → `decision_result=reship`）。

### 缺口 4 · 转人工后买家被永久锁死、且无人接手（**2026-10-15 二次验收发现**）

**触发场景**：会话 `DEMO001` 在 `LLM_ENABLED=false` 期间转人工（`escalated_reason=tool_failed`），
之后打开买家页面，输入框永久灰掉、页面卡在终态 —— 「一直留在那个界面」。

**三条叠加的缺陷**：

1. **转人工后没有人接手** —— `session.escalate()` 只改会话状态，`assignee` 保持 `None`。
   指挥台显示"已转人工"，却没有任何人被指派，买家等的是一个不会出现的人；
2. **终态没有出口** —— `case_id = order_id` 是入口幂等键，**同号重开会恢复同一条已终结会话**；
   H5 又在转人工时锁死输入 → 买家被永久卡死；
3. **`CLOSED` 前端不可见** —— `applyServerSnapshot` 把 `CLOSED` 也当作非 escalated 且不置 `ended`。

**已实施**：

- `session.escalate()` 同时置 `assignee=manual`（**转人工＝有人接手**）；护栏触发的转人工也同步
  `workflow_status=escalated`，指挥台可见待处理工单；
- H5：**转人工后不再锁输入**（人工接手期间买家仍要能补充信息，否则"转人工"只是单向告知），
  仅 `CLOSED` 锁死；新增**「重新开始」出口**（清空本地态回到开始区，并提示"换一个订单号即可开始新会话"）；
  `ESCALATED` 与 `CLOSED` 在快照里分开处理。

**验收**：`verify_h5.cjs` 新增 5 项（转人工可留言 / 已结束关闭 / 重开出口 / 非终态不显示 / 已结束文案）。

**历史数据的补救路径**：改动前留下的终态会话（`assignee=None`）不会被自动修复，
但管理员在指挥台对该工单**发一条人工消息**即可把它接管过来（`assignee` 转为 `manual`），
之后买家就能继续对话；或由买家点「重新开始」换一个订单号。

### 缺口 5 · 瞬时失败被打成"已转人工"（**2026-10-15 二次验收发现**）

**问题原状**：模型调用抛异常时（`kind=model_error`），`orchestrator` 与 `model_unavailable` 一同
把 `workflow_status` 打成 `escalated`。于是指挥台出现自相矛盾的状态——
**工单"已转人工" / 处理者 `—` / 会话仍 `CLARIFYING` / 买家输入仍可用**，而且没有任何人被指派。
模型瞬时失败（回复本身就是"请再说一次"）本就不等于"该转人工"。

**已实施**：`model_error` **不转人工** —— 保持 `workflow_status=agent_running`，
另落一条 `model_error` 护栏事件便于排查模型侧问题；买家重试即可。
`model_unavailable`（模型未配置）与 `gate_paused`（成本暂停）仍转人工，语义不变。

**同批修正**：演示夹具的 `already_exists` 分支原先**重新合成**事实，导致界面显示的金额/类目
（DEMO002 显示「家居日用 ¥19.9」）与规则实际使用的事实（「手机壳 ¥199」）不一致。
已改为读回真实注入的事实（`tools/order.peek_order`）。

### 缺口 6 · 转人工后工单「只进不出」（**2026-10-15 三次验收发现**）

**问题原状**：`escalated` 此前是一个**没有任何出口**的状态。

- 前端 `renderOpBar` 在该分支**只渲染一句提示**（"已转人工，由管理员接管处理。"），没有按钮；
- 后端也没有任何动作接受它：`confirm` 要求 `awaiting_confirm`、`dispatch` 只收 `queued/agent_running`、
  `intervene` 对已是 `escalated` 的工单只是**再置一次**（no-op）。

后果：**一笔工单只要转人工，就再也无法推进**——既不能结案，也不能交回智能体。
这既让演示流程走不通，也违反政策 C5 对「保留撤销 / 召回」的要求。

**已实施**：新增三个出口动作（各对应一条会话/工单语义清晰的转移）。

| 动作 | 端点 | 语义 | 守卫 |
| --- | --- | --- | --- |
| **接管** | `POST /api/console/cases/{id}/takeover` | 明确归属到人工 | 已完结则 409 |
| **退回智能体** | `POST /api/console/cases/{id}/resume` | **撤销转人工**：会话脱离终态 → `CLARIFYING`，工单回 `agent_running`，`assignee=agent` | 仅 `escalated`；**买家主动要求人工（`buyer_request`）时拒绝**（409 `buyer_wants_human`） |
| **人工结案** | `POST /api/console/cases/{id}/close` | 管理员处理完毕 → `resolved` | 已完结则 409 |

两条设计取舍（刻意的）：

1. **买家意愿优先于效率**：`buyer_request` 时不提供"退回智能体"——把明确要求人工的买家推回给机器人，
   是拿效率推翻用户意愿。此时只能接管或结案。
2. **退回必须同时撤销会话终态**：否则工单虽退回，会话仍是 `ESCALATED`，买家一发消息又被"会话已结束"挡回——
   这正是缺口 4 的病根，改一半等于没改。

**会话出口落在 `session.resume_from_escalation()`**（会话维度），指挥维度（`workflow_status`/`assignee`）
由 `console` 层改——两个状态机各自闭环，互不越界。

**踩到的一处陷阱**：`chat_repo.update_case` 用 `None` 表示"本字段不更新"，
因此**清空 `escalated_reason` 必须传空串**，传 `None` 会静默保留旧值。

**验收**：`test_console.py` C12—C16（13 项断言，含"买家要求人工时拒绝退回"与"重复结案 409"）；
`verify_console.cjs` 新增 3 项（三个出口按钮齐备、各自带 `data-op`、`buyer_request` 时不可点退回）。

## 五、验收标准与演示脚本（定死）

作品档位下，验收不数功能个数，只回答四个问题：

## 六、边界声明（明确不做）

- 不做真实电商系统对接——无数据源、无商家授权，数据走**仿真 fixture**；
- 不做多 Agent 矩阵、不做多模态视频理解、不做全链路跟单；
- 不做真实资金动作——保持影子模式；
- 不做**规则写不成表**的场景（创意、谈判、纠纷定性）——那是本智能体的能力边界之外；
- 不做上线运营所需的生产要件扩张（分布式幂等、多实例检查点迁移、C 端并发容量）。

> 「不做」不等于「不保留」。现有业务壳（指挥台 / 复核工作台 / 审计 / 双闸门）降级为**可选外壳**，是复用路线的现成资产，不删除。

### 演示模式（买家界面开关）

买家助手界面提供「演示模式」开关，用于**把智能体测透**：开启后不论输入什么订单号，都按
「该订单存在」受理——后端按订单号**确定性**（sha256）合成订单 / 物流 / 画像事实，
同一订单号恒得同一份数据，**换个订单号即换一组事实**，从而覆盖不同规则分支。

三条不可让步的边界：

| # | 边界 | 落点 |
| - | - | - |
| 1 | **不伪装数据** | 合成事实一律带 `synthetic=true`；界面用醒目暖色徽标标注"演示模式 · 非真实订单" |
| 2 | **不污染真实链路** | 已配置 `ORDER_API_BASE` / `LOGISTICS_API_BASE` 时整体失效（建单直接拒绝） |
| 3 | **不覆盖既有事实** | 订单已存在则原样返回（`reason=already_exists`），不重写；且**读回真实注入的事实**回显给界面，不另算一份合成值 |

服务端未开启（`DEMO_ANY_ORDER=false`）时建单返回 **403** 并说明原因，不静默降级为"数据不足"。

**验证脚本与计费的边界**（避免自动化验证自身产生费用）：

| 脚本 | 是否打真实后端 | 模型开启时是否计费 |
| - | - | - |
| `backend/tests/test_*.py` | 否（假仓储 / 桩） | **否**（测试内强制关闭模型或注入桩） |
| `frontend/verify_console.cjs` ①②③ | ①③ 打只读端点 | **否**（不触发对话） |
| `frontend/verify.cjs` ①② | 部分打后端 | 问答段在 `QA_LLM_POLISH=true` 时**自动跳过** |
| `frontend/verify_h5.cjs` ③ | 打对话端点 | 入口开启时**整段自动跳过** |
| 真实对话 / 问答 / 视觉请求 | 是 | **是**（属使用者的测试范围） |
