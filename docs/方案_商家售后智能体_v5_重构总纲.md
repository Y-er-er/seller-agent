### 3.2 行业共识（现阶段能力边界）

1. **从"回答问题"到"办成事"**——Agent 直接调用业务系统完成退款/改址/补发，闭环执行；
2. **多 Agent 分工协作**——客服 / 导购 / 跟单 / 质检各司其职；
3. **主动服务**——催付、催单、挽单、风险预警；
4. **多模态**——图片、故障截图、视频理解；
5. **商家侧价值可量化**——人工介入率、响应时长、处理时长、转化率。

### 3.3 我们的差异化定位（**不追头部全能**）

> 头部产品是**广覆盖的客服 Agent**；我们做**聚焦的"售后处置决策 Agent"**——专攻**"该不该赔、赔多少、怎么赔"**，把**判定确定性与人机协同做到可审计**。

这恰是头部产品**最弱的一环**：它们多为规则与模型混合、结论不可解释、无法逐条回溯。我们的护城河不在"覆盖多少意图"，而在**"每一条结论都能给出规则级依据，且同输入必同结论"**。

## 五、七条工程红线（继承 v4，全部保留）

1. **不做质量判定**：质量争议一律转人工；模型只能描述可见事实。
2. **规则引擎不暴露为模型工具**：模型只能"请求判定"，不能"改写规则/阈值"。
3. **资金动作双闸门**：`SHADOW_MODE=false` **且** `DISPOSAL_ENABLED=true` 才具资格，且带幂等键。
4. **同输入同结论**：仅约束**判定**；对话过程允许非确定性。
5. **个人信息最小化**：模型调用可全局关闭。
6. **成本闸门**：`LLM_ENABLED` 总开关 + 护栏参数。
7. **成本控制不侵蚀智能体架构**：**模型自主决定是核心**——意图理解、工具选择、追问策略、提交时机由模型自主，不得为省成本改成线性编排。成本控制只作用于**运行策略**（默认关闭 / 离线桩优先 / 真机最小化 / 上下文工程 / 闸门兜底）。

> 加上 §2.2 的**六条合规红线**，共 **13 条**不可让步项。

## 六、系统架构（重划四层边界）

```
L1  界面层
    ├─ 商家指挥台（收件箱 / 卷宗 / 确认）——主界面
    └─ 买家 H5 入口（对话 / 上传 / 转人工）

L2  Agent 编排层（重构焦点）
    ├─ 护栏（轮数 / 字数 / 合规身份明示）
    ├─ 成本闸门（调用前预检 + 调用后记账）
    ├─ agentic 循环（模型 ⇄ 工具，手写 StateGraph）
    ├─ 记忆（会话上下文 + 工单阶段）
    └─ 槽位抽取 + 参数装配
         │  唯一出口：submit_for_decision

L3  判定内核（保留，v2.x 资产）
    intake → fetch → evidence(可关) → judge → risk → dispose → audit
    返回：结论 + 命中规则 + 逐条依据（hit_details）

L4  数据层
    conversation_case / _message / case_slot / guardrail_event / llm_usage
    decision_audit · checkpointer
```

| 层间约束 | 说明 |
| - | - |
| **单向调用** | L2 **只能**通过 `submit_for_decision` 触达 L3，**不得直接读判定内部状态** |
| **判定层无状态** | L3 不知道对话存在，保持可复现 |
| **循环手写** | 不用 `create_agent`——成本预检、审计、硬终止必须不可绕过 |
| **命名空间隔离** | 对话线程与判定线程检查点分开 |
| **关联键统一** | `case_id` = 受理号 = 判定图 `thread_id` = 审计检索键（四处同值） |
