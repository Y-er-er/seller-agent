## 一、先解决"语义混乱"——这是项目混乱的微观根源

我把代码通读后发现：项目**最大的混乱不在架构，而在名词**。同一个中文词在不同的文件里指不同的东西，导致"看起来做完了、其实没接通"。

### 1.1 五个必须分清的维度

| # | 维度 | 键名（建议） | 取值 | 现有载体 |
| - | - | - | - | - |
| 1 | **问题原因**（为什么） | `issue_reason` | 未收到货 / 质量问题 / 错发漏发 / 无理由 / 其他 | `models.RefundReason` |
| 2 | **问题对象**（出在哪） | `issue_object` | 商品本身 / 包装 / 物流 / 其他 | 槽位 |
| 3 | **诉求方向**（想要什么） | `claim_direction` | 仅退款 / 退货退款 / 补发 / 换货 / 部分退款 | `models.ClaimType` |
| 4 | **判定结论**（规则怎么定） | `conclusion` | auto_pass / auto_reject / request_evidence / to_human | 规则引擎 |
| 5 | **处置动作**（最终干什么） | `disposal` | refund / reship / reject / manual / pending_evidence | `resolve_disposal` |

> **关系**：`disposal = f(claim_direction, conclusion)`；`issue_reason` / `issue_object` 只影响 `conclusion`。**五者不得互相替代**。

### 1.2 现存命名撞车（★ 必须修）

| 位置 | 现状 | 问题 |
| - | - | - |
| `chat/slots.py` | `SLOT_CLAIM_TYPE = "claim_type"`，取值却是「未收到货 / 质量问题 / 错发漏发 / 无理由 / 其他」 | **名字说"诉求"，装的是"原因"** —— 与 `models.ClaimType`（真诉求方向）**同名不同义** |
| `chat/slots.py` | `SLOT_EXPECTATION = "expectation"`，取值「仅退款 / 补发 / 换货 / 其他」 | 这才是**真正的诉求方向**，却叫"期望方案"，且枚举缺「退货退款」 |

**修法（一次到位，不做别名兼容）**：

```
SLOT_ISSUE_REASON      = "issue_reason"       # 原 claim_type（原因）
SLOT_CLAIM_DIRECTION   = "claim_direction"    # 原 expectation（方向）
CLAIM_DIRECTIONS = ("仅退款", "退货退款", "补发", "换货", "其他")
_DIRECTION_TO_CLAIM = {"仅退款": REFUND, "退货退款": RETURN_REFUND,
                       "补发": RESHIP, "换货": EXCHANGE, "其他": REFUND}
```

【待商讨 Q1】是否接受这次"破坏性改名"？——它会让旧槽位数据（若已有）读不出，但项目全是 mock，我判断**代价为零、收益极大**。

## 二、代码缺陷实证（"判定扩展已完成"是个假象）

我按调用链逐个核对，以下 6 条是**真实存在的断链**，每条都可复现：

| # | 缺陷 | 证据（文件:行） | 后果 |
| - | - | - | - |
| **D1** | 诉求方向**从未写入** `RefundRequest` | `slots.py:205` `assemble_request` 不接收 direction，`RefundRequest(...)` 未传 `claim_type` → 恒为默认 `REFUND` | **补发规则 R9/R10 永远命中不到** —— 三类判定形同虚设 |
| **D2** | 指挥台硬编码诉求方向 | `orchestrator.py:221` `intent = "refund"`（注释自认"骨架阶段默认退款"） | 指挥台确认的处置**永远不可能是补发** |
| **D3** | `submit_for_decision` 收集的槽位里没有 direction | `tools.py:300-310` 收集 `claim_type/issue_object/expectation`，但 `expectation` 未参与装配 | 模型即使正确抽取了"补发"，也无处落地 |
| **D4** | 确认不触发处置执行 | `console.py:103-117` `confirm()` 只 `update_case(workflow_status=resolved)` | **资金/库存动作悬空** —— "该退的没退、无人跟进"（正是 v5 §5 红线 3 要防的） |
| **D5** | 系统提示词仍是"仅退款" | `agent.py:61` `"正在处理订单 {order_id} 的「仅退款」咨询"` | 模型认知与三类判定不一致，会拒绝处理补发诉求 |
| **D6** | 合规能力完全缺失 | 全代码库无身份明示 / 内容标识 / 180 天留存 | 不满足 C1—C3，见 §7 |

> **结论**：所谓"第一步判定扩展已完成"，实际只完成了**规则层**（R9/R10/R11 + `resolve_disposal` 纯函数 + 单测），**接入层与编排层从未接上线**。这不是实现质量问题，是**改向时只改了局部、没有端到端验收**。

## 三、目标数据流（端到端，逐跳可验）

```
① 买家在 H5 入口发问
      └─ 后端创建/复用 case（case_id = order_id = thread_id = 审计键）
② 消息进入工单收件箱（workflow_status=queued）
③ 管理员在指挥台「指派」→ workflow_status=agent_running
④ 智能体接管，跑 agentic 循环
      ├─ model_step：自主决定调用 query_order / query_logistics / ...
      ├─ tool_step：如实回灌结果
      └─ submit_for_decision(claim_direction, issue_object, issue_reason, ...)
             └─ assemble_request → RefundRequest(claim_type=方向)  ← D1 修复点
                    └─ 判定图 ainvoke（thread_id=受理号，幂等）
                           └─ 返回 conclusion + hit_rules + hit_details
⑤ disposal = resolve_disposal(claim_direction, conclusion)   ← D2 修复点
⑥ 工单 → awaiting_confirm（结论 + 金额落库）
⑦ 管理员「确认」
      └─ 授权分级 L1/L2/L3 判定
      └─ L1 且双闸门开 → 调处置工具执行（幂等键 = case_id）  ← D4 修复点
      └─ 影子模式 → 只记录 "本应执行"，不产生外部调用
⑧ 审计落库（decision_audit + 分级授权字段）→ 工单 resolved
```

**任一跳失败的行为**（沿用 v5 §5 红线）：
- 取数失败 → 返回 `available=false`，交规则转人工；
- 判定失败 → 保留会话状态，可重试；
- **处置失败 → 升 escalated，绝不当成功**。

## 四、两套状态机与映射

现有两套状态机是**正交**的（设计正确，保留）：

| 状态机 | 载体 | 语义 | 状态 |
| - | - | - | - |
| **会话状态机** | `conversation_case.status` | 这笔**沟通**走到哪 | CREATED→CLARIFYING→COLLECTING→SUBMITTED→DECIDED / ESCALATED / CLOSED |
| **工单状态机** | `conversation_case.workflow_status` | **谁在处理**、指挥到哪 | queued→agent_running→awaiting_confirm→resolved / escalated |

【待商讨 Q2】两套状态机并存，指挥台要同时读两个字段（前端已做）。**是否合并为一套**？
- 合并优点：前端与运维只需理解一套；
- 不合并优点：会话（买家视角）与工单（商家视角）语义确实不同，合并会丢失信息。
- **我的建议：保留两套，但在指挥台暴露一个"派生阶段"字段 `stage`**（由两者确定性映射），前端只读 `stage`。这样既不丢信息，也不让业务岗面对两套状态。

## 五、判定与处置：三类判定 + 三级授权

### 5.1 三类判定（D1/D2/D3 修复后的真实闭环）

| 诉求方向 | conclusion=auto_pass | auto_reject | to_human / request_evidence |
| - | - | - | - |
| 仅退款 | refund | reject | manual / pending_evidence |
| 退货退款 | refund（先退后款） | reject | manual / pending_evidence |
| **补发** | **reship** | reject | manual / pending_evidence |
| 换货（P3） | exchange | reject | manual |
| 部分退款（P3） | partial_refund | reject | manual |

### 5.2 三级授权（对应政策"三层决策权限"，C4）

| 级别 | 条件 | 智能体权限 | 兜底 |
| - | - | - | - |
| **L1 全自主** | `auto_pass` 且 金额 ≤ ¥300 且 无风险标签 且 该诉求方向已启用 | 可直接执行 refund / reship | 审计 + T+1 可撤销 + 抽样复核 |
| **L2 需确认** | 中额 / 首单 / 异常 | 发起动作并挂起，人工确认 | HITL |
| **L3 禁止** | 质量问题 / 大额 / 法律敏感 / 威胁投诉 | 只能转人工 | 人工全权 |

【待商讨 Q3】L1 阈值 `¥300` 沿用既有 `AUTO_AMOUNT_CAP`，但**补发没有金额概念**（是库存动作）。我的建议：补发按**商品成本的等价金额**判定级别（用订单实付额近似），并在审计里记 `auth_basis=amount_equivalent`。是否接受？

## 七、合规实现（C1—C6 逐条落点）

| 红线 | 落点 | 具体做法 | 验收 |
| - | - | - | - |
