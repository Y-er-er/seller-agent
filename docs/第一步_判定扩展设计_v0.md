# 第一步 · 判定扩展设计（仅退款 → 拒绝/退款/补发）v0

> **状态**：**设计稿，待确认后实施**（纪律 1：先方案后编码）
> **日期**：2026-10-15 · **依据**：《方案_商家售后智能体_v4.md》§三

---

## 一、目标

把判定结果从"仅退款"扩为 **拒绝 / 退款 / 补发** 三类，并**离线验证准确率**。

## 二、现状（已核对代码）

| 项 | 现状 |
| - | --- |
| 结论 `CONCLUSIONS` | `auto_pass` / `auto_reject` / `request_evidence` / `to_human`（4 类） |
| 原因码 `RefundReason` | `not_received` / `quality` / `wrong_item` / `no_reason` / `other`（5 类，是**原因**不是**诉求**） |
| 事实字段 `FACT_FIELDS` | 17 个，**无"诉求分类"** |
| 处置 | 仅"仅退款"一种 |

**缺口**：没有"买家想要什么处置"（退款 vs 退货退款 vs 补发 vs 换货）这个维度，所以补发/换货/退货退款无法表达。

## 三、扩展设计（结论与处置分层，最小侵入）

### 3.1 新增「诉求分类」`claim_type`

```python
class ClaimType(str, Enum):
    REFUND = "refund"              # 仅退款（不退货）
    RETURN_REFUND = "return_refund" # 退货退款（退货后退款）
    RESHIP = "reship"              # 补发 / 重发
    EXCHANGE = "exchange"          # 换货
    PARTIAL_REFUND = "partial_refund"  # 部分退款 / 差价补偿
```

- `RefundRequest` 增字段 `claim_type`（默认 `REFUND`）。
- **事实字段键命名为 `claim_intent`**（避免与既有槽位 `claim_type` 撞名，见 §七 命名地雷）。
- **第一步只落地 `REFUND` / `RETURN_REFUND` / `RESHIP` 三类**；`EXCHANGE` / `PARTIAL_REFUND` 预留枚举、P3 再开。

### 3.2 新增「处置结果」`disposal_result`（与结论分层）

```python
DISPOSAL_RESULTS = ("refund", "reship", "reject", "manual", "pending_evidence")
```

**处置 = f(诉求, 结论)**，确定性映射（**模型不参与**）：

| claim_type ↓ \ 结论 → | auto_pass | auto_reject | request_evidence | to_human |
| - | - | - | - | - |
| refund | **refund** | reject | pending_evidence | manual |
| return_refund | **refund**（退货后退款） | reject | pending_evidence | manual |
| reship | **reship** | reject | pending_evidence | manual |
| exchange | exchange | reject | pending_evidence | manual |
| partial_refund | partial_refund | reject | pending_evidence | manual |

### 3.3 新增补发判定规则（R9 / R10）

补发与"退款"的差别在于**诉求分类**——同一"物流损坏/漏发"，诉求是补发就补发、是退款就退款。

| 规则 | 条件（示意） | 结论 |
| - | --- | --- |
| **R9 补发通过** | `claim_type == reship` 且（`refund_reason_code == wrong_item` 或 物流异常）且金额 ≤ 补发上限 | `auto_pass` |
| **R10 补发超限转人工** | `claim_type == reship` 且金额 > 补发上限 | `to_human` |

> ⚠️ 补发上限等阈值需新配置变量（如 `RESHIP_AMOUNT_CAP`），**沿用纪律 9（入 .env，不硬编码）**。

### 3.4 兼容性（现有规则不动）

- 现有 R1—R8 **原样保留**（仅退款路径），新增的 `claim_type` 维度**只增不改**；
- 结论枚举 `CONCLUSIONS` **不变**（补发通过仍落 `auto_pass`，处置层再映射为 `reship`）；
- 这样**零破坏既有 344 项判定回归**，扩展是纯增量。

## 四、准确率验证方案（离线，零模型调用）

## 七、⚠️ 命名地雷（实施中发现，待后续清理）

- 既有槽位 `SLOT_CLAIM_TYPE = "claim_type"` 实为**原因**（未收到货/质量/错发漏发），映射 `RefundReason`，**名不副实**；
- 真正的"诉求方向"（退款/补发/换货）在槽位里是 `SLOT_EXPECTATION`（期望方案）；
- 视觉信号 `llm/client.py` 的 `claim_type`（quality/damage/wrong_item…）又指"图片问题类型"。
- **三者同名不同义**，是历史遗留命名债。本次**未动**（避免牵连 5 文件 + 2 测试），仅把新事实字段改名为 `claim_intent` 绕开；
- **建议后续单独清理**：槽位 `claim_type` → `reason`，视觉信号 → `image_issue`，统一"claim_type"专指诉求方向。
