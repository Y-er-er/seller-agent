## 零、先澄清两个容易混淆的事

### 0.1 「嵌入真实商城页」≠「商家能控制商品」

商家控制商品靠的是**写接口**，不是"看到页面"：

```
看到页面 ──→ 只是展示        （改不了任何东西）
调写接口 ──→ 真的改数据      ← 这才是"控制"
```

所以"把真实商城的商品页嵌进卖家后台"这件事，对"控制产品"**毫无帮助**。
它的问题不是"技术上做不到"，而是**做完了也没用**。

### 0.2 真正要接的是两类接口

| 方向 | 用途 | 现实可行性 |
| --- | --- | --- |
| **读**（商品 / 订单 / 物流 / 买家） | 陈列页显示真实数据、售后统计用真实订单 | ✅ 多数平台开放 |
| **写**（改价 / 上下架 / 库存） | 商家控制商品 | ⚠️ **受限**：多数平台不开放第三方写，需官方 ISV / ERP 授权 |

**本项目的定位（明确写下来）**：

> 我们做**经营决策台**：理解需求 → 判断该改什么 → 生成文案/算定价 → **记录决策**
> **执行**：有写权限时调写接口；没有时**导出给人一键粘贴**。
> 无论哪种，**决策链路都可审计**（`operation_log` + `pending_action`）—— 这是我们的价值，不依赖平台开放写权限。

## 一、现状差距

| 数据域 | 现状 | 真实形态 | 结论 |
| --- | --- | --- | --- |
| 商品 | **无外部源**（卖家自建） | SPU→**SKU**、类目树、多图、划线价 | ❌ 需新增 `GoodsSource` |
| 订单 | `OrderSnapshot` **一个订单一个商品** | 订单头 + **订单行（一单多商品）** | ❌ **结构要改** |
| 金额 | `float` | **整数分** | ⚠️ 新字段用分，旧字段保留 |
| 库存 | `goods.stock` 单值 | **多仓 / 预占** | ❌ 不做（见 §五） |
| 物流 | 单运单 | 多包裹 | ⚠️ 暂不扩 |
| 售后 | 我们**自己产生**的工单 | 平台存量工单 | ⚠️ 属"导入"不是"对接" |

## 二、订单行（一单多商品）

### 2.1 真实结构

```
订单头 order
  ├─ 订单行 1: goods_no=G-0001 × 2  实付 ¥158.00
  ├─ 订单行 2: goods_no=G-0004 × 1  实付 ¥10.00
  └─ 订单行 3: goods_no=G-0006 × 1  实付 ¥30.00
合计 ¥198.00
```

**售后通常挂"订单行"而不是"订单"** —— 退一件不等于退整单。这是现在模型最大的偏差。

### 2.2 模型改动（**向后兼容**）

```python
class OrderItem(BaseModel):
    line_id: str = ""          # 平台订单行 id（用于售后关联）
    goods_no: str = ""         # 对应卖家控制台的 goods.goods_no
    sku_id: str = ""           # 平台 SKU（我们暂不建 SKU 表，仅透传）
    title: str = ""
    quantity: int = 1
    unit_price_cent: int = 0   # 单价（分）
    paid_cent: int = 0         # 该行实付（分，含优惠分摊）

class OrderSnapshot(BaseModel):
    order_id: str
    items: list[OrderItem] = []      # ★ 新增：一单多行
    item_category: str = ""          # 兼容字段（单行订单场景）
    goods_no: str = ""               # 兼容字段（单行订单场景）
    pay_amount: float = 0.0          # 兼容字段
    ...
```

**为什么保留 `goods_no` / `item_category`**：

- 现有**售后判定链**（R1—R11）是按"订单的主商品"写的，改动面很大；
- 保留它们 = **现有 25 个测试与判定逻辑零改动**（向后兼容）；
- 语义写清：**只在单行订单时有值**；多行订单要用 `items`。

### 2.3 判定层的已知简化（必须标注）

```
多商品订单的售后归因 = 取「金额最大的那一行」作为主商品
```

**这是简化，不是正确做法**。正确做法是工单直接挂 `line_id`。
写在这里，是为了让后来人知道"这块不是没想过，是**故意延后**"。

**后续演进**：`conversation_case` 加 `line_id` 字段（已有 `goods_no`，加一行的事），
判定时优先按行算，取不到再回落到主商品。

## 三、GoodsSource 端口（商品只读源）

### 3.1 接口

```python
class GoodsSnapshot(BaseModel):
    goods_no: str                        # 平台编号（**upsert 的唯一键**）
    title: str = ""
    category: str = ""                   # 平台类目（多级树扁平后的**最后一级**）
    price_cent: int = 0                  # 售价（分）
    list_price_cent: int = 0             # 划线价（分）
    stock: int = 0
    status: str = ""                     # on_shelf / off_shelf / draft
    description: str = ""
    images: list[str] = []               # 平台 CDN 图 URL
    updated_at: datetime | None = None   # **增量同步靠它**

class GoodsSource(Protocol):
    async def fetch_goods(self, goods_no: str) -> GoodsSnapshot | None: ...
    async def list_goods(self, *, updated_since: datetime | None = None,
                         limit: int = 200) -> list[GoodsSnapshot]: ...
    async def fetch_categories(self) -> list[dict[str, Any]]: ...
```

### 3.2 同步策略

| 项 | 选择 | 理由 |
| --- | --- | --- |
| **方向** | **只读**（平台 → 本地） | 写权限受限（见 §0.2），不做"双向同步"的假承诺 |
| **触发** | **拉模式**：定时（如 10 分钟）+ 手动「同步」按钮 | 推模式要公网入口 + 验签，成本高、收益低 |
| **粒度** | `updated_since` **增量** | 全量拉商品在真实店铺是几千条，拉不动 |
| **幂等键** | `goods_no`（upsert） | 与现有 `goods.goods_no` 天然对齐 |
| **图片** | **转存到自己的存储**，不直接引用平台 CDN URL | 平台 URL 会过期/防盗链；且售后统计要长期可查 |
| **冲突** | **平台为准**，覆盖 `title/price/stock/category/status/images`；**`description` 也覆盖，但记 `operation_log`（actor=system）** | 覆盖可审计、可追溯，比"悄悄覆盖"安全 |

### 3.3 与现有结构的关系

```
平台商品 ──(同步)──→ goods 表
                       ├─ goods_no      ← 幂等键
                       ├─ title/price/stock/category/status
                       ├─ description   ← 同步覆盖（可审计）
                       └─ 本地独有：sort_no / stock_alert / 回收站 deleted_at
```

**本地独有字段不被覆盖** —— 它们是"经营偏好"（排序、预警线），平台不管这些。

## 五、明确不做（边界）

| 不做 | 原因 |
| --- | --- |
| **SKU 表** | 真实商品一个款多规格。做 SKU 要重写商品/库存/订单行全部链路，属"另一个量级"；当前 `sku_id` 仅**透传** |
| **多仓库存** | 同上，且需要仓储系统对接 |
| **双向同步（我们写回平台）** | 写权限受限，做"半吊子双向"比不做更危险（容易状态不一致） |
| **平台存量售后单导入** | 属"数据迁移"项目，不是接口对接 |
| **嵌入平台商城页面** | 见 §0.1 —— 对控制商品无用 |

---

## 六、遗留风险（写清，不藏）

1. **判定层仍按"主商品"归因** —— 多商品订单的部分退款会算到主商品头上（见 §2.3）
2. **`pay_amount` 仍是 float** —— 与新的 `*_cent` 字段并存，容易出现"两套金额口径"
   → 建议第 2 步一起改成整数分，并加一条测试锁住
3. **`GoodsSource` 只读** —— 若将来平台开放写权限，"写适配器"是独立设计，不能塞进这个端口
