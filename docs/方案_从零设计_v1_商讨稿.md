## 一、第一性原理：问题与目标

### 1.1 问题（从业务倒推）

商家每天收到大量售后诉求（退款 / 退货退款 / 补发 / 换货）。处理它需要三件事：

1. **沟通**：搞清买家到底要什么（自由文本 → 结构化诉求）；
2. **取证**：查订单、查物流、看材料，确认事实；
3. **决策与执行**：判断该不该赔、赔多少、怎么赔，然后真的去做。

现状是：**纯人工**慢且口径不一；**纯 AI** 不敢放权（赔错钱是真实损失）。

### 1.2 目标（一句话）

> 让智能体接管**过程**（沟通 / 取证 / 查单），让**规则 + 人**掌管**结论**（赔不赔），并保证每一笔都**可解释、可追溯、可撤销**。

### 1.3 非目标（明确不做）

不做质量判定 · 不做多语言 · 不做小程序 / IM · 起步阶段不接真实库 · 视觉理解按需评估（费用项，开启前单独确认）· 不追求"覆盖所有意图"。

> ⚠️ **前一版本在此处罗列了"零模型调用 / 零现金支出"等条目，属概念错误**：那些是上一版的自设护栏，不是需求。
> 成本是**配置项**，不是**设计前提**。

## 二、领域模型（★ 从零设计的第一性产物）

**先把"世界里有哪些东西"定清楚，后面所有设计都从它派生。**

### 2.1 七个核心实体

| # | 实体 | 是什么 | 关键属性 | 何时产生 |
| - | - | - | - | - |
| 1 | **工单 Case** | 一笔售后诉求的生命周期载体 | `case_id`（受理号）· `order_id` · `merchant_id` · `stage` | 买家发起 |
| 2 | **诉求 Claim** | 买家想要什么（**结构化三件套**） | `direction`（方向）· `reason`（原因）· `object`（对象） | 沟通中逐步抽取 |
| 3 | **事实 Fact** | 判定的输入，只读权威 | 订单快照 · 物流 · 买家画像 · 材料清单 | 取证时取回，快照固化 |
| 4 | **判定 Decision** | 规则对"赔不赔"的回答 | `conclusion`（四值）· `hit_rules` · `details` | 提交内核时一次性产生 |
| 5 | **处置 Disposal** | "最终干什么" | `action`（refund/reship/reject/manual/…） | 由 (主张, 结论) 确定性映射 |
| 6 | **授权 Authorization** | 这笔动作谁批的 | `level`（L1/L2/L3）· `basis` · `by` | 执行前判定 |
| 7 | **审计事件 AuditEvent** | 不可变的"发生了什么" | `stage` · `at` · `payload` · `retention_until` | 每次关键动作追加 |

### 2.2 实体关系（不可变式）

```
Case ─1:1─ Claim          一笔工单只有一个最终诉求（可被沟通修正，修正留痕）
Case ─1:1─ Fact           事实以**快照**形式固化，判定时不再重取（保证可复现）
Case ─1:1─ Decision       判定**只能产生一次**（幂等），重复提交返回既有结论
Case ─1:1─ Disposal       disposed = f(claim.direction, decision.conclusion)
Case ─1:1─ Authorization  一笔处置一次授权判定
Case ─1:N─ AuditEvent     只追加，永不修改
```

### 2.3 ★ 奠基性问题 F1：诉求三件套是否够用？

我提议 **direction + reason + object** 三件套。理由：
- `direction` 决定**处置方向**（退款还是补发）；
- `reason` 决定**判定理由**（质量问题 → 红线转人工）；
- `object` 决定**责任归属**（物流问题 vs 商品问题）。

**风险**：真实售后可能还需要「责任方」「金额诉求」「时限」等。是否要扩成四件套（加 `claim_amount`）？

> **我倾向：先三件套 + `claim_amount` 可选项**（不退超过实付）。请你判断这是否足够覆盖你想做的场景。

## 三、能力清单与边界

### 3.1 六项能力（这就是"这个智能体干什么"）

| # | 能力 | 输入 | 输出 | 自主度 |
| - | - | - | - | - |
| 1 | **接单** | 渠道消息 | 工单入收件箱 | 自动 |
| 2 | **沟通** | 买家消息 | 结构化诉求（三件套） | **模型自主** |
| 3 | **取证** | 工单 | 事实快照 + 材料清单 | **模型自主选工具** |
| 4 | **判定** | 事实 + 诉求 | 结论 + 逐条依据 | **确定性代码** |
| 5 | **处置** | 诉求 + 结论 | 退款/补发/拒绝/转人工 | **分级授权** |
| 6 | **协同** | 管理员指令 | 指派/介入/确认/驳回 | **人在环** |

### 3.2 边界（负面清单，写进设计）

模型**不能**：改规则、改阈值、直接退款、看别的工单、编造事实。
系统**不能**：自动放过质量问题、自动执行未授权资金动作、把失败当成功。

## 四、三条不可逾越的线（从零重述）

| 线 | 内容 | 违反后果 |
| - | - | - |
| **结论线** | 赔不赔由**规则**定，模型不参与任何阈值判定 | 同输入不同结论，不可审计 |
| **执行线** | 资金/库存动作必须**授权 + 幂等 + 可撤销** | 重复退款、资金悬空 |
| **自主线** | **过程自主，结论确定** | 越权 or 僵化 |

> 补充第四条（政策新增）：**合规线** —— 身份明示 / 内容标识 / 日志留存 ≥180 天（C1—C3）。

## 五、分层架构（★ 从零设计）

我提议 **四层 + 一内核 + 一旁路**：

```
┌──────────────────────────────────────────────┐
│ ① 渠道层   买家 H5 入口（后期：平台客服）        │  只负责"消息进出"
├──────────────────────────────────────────────┤
│ ② 协同层   指挥台：收件箱 / 指派 / 介入 / 确认 / 卷宗 │  只负责"人的指挥"
├──────────────────────────────────────────────┤
│ ③ 智能体层 对话 · 槽位 · 工具 · 护栏 · 成本        │  模型自主；唯一出口＝请求判定
├──────────────────────────────────────────────┤
│ ④ 决策内核 事实 → 规则 → 结论 → 处置映射（纯函数）  │  无状态、可复现、不认识对话
├──────────────────────────────────────────────┤
│ ⑤ 执行层   授权分级 → 双闸门 → 执行 → 可撤销       │  只被"处置结果"驱动
└──────────────────────────────────────────────┘
                 ↓ 全层写入（只追加）
      ⑥ 审计旁路（含合规留存）  旁路：失败不阻断主流程
```

### 5.1 层间三条契约（这是从零设计里最关键的改良）

| 契约 | 内容 | 为什么 |
| - | - | - |
| **C-1 唯一出口** | 智能体层**只能**通过 `submit_for_decision` 触达决策内核，不得读内核内部状态 | 防模型越权；内核可独立测试 |
| **C-2 显式方向** | 请求判定的入参**必须**含 `claim.direction`，内核不得默认 | 上一版正是因为默认 `refund` 导致补发永远无效 |
| **C-3 旁路审计** | 审计写入**吞异常**，绝不阻断主流程；但**读审计**必须透出异常 | 写不阻断、读不静默（两条语义不同） |

### 5.2 ★ 奠基性问题 F2：决策内核是"库"还是"服务"？

| 选项 | 优点 | 缺点 |
| - | - | - |
| ① **同进程库**（函数调用） | 简单、零网络、易测 | 与智能体同生共死 |
| ② **独立服务**（HTTP） | 可独立部署、多智能体共享 | 多一跳、运维复杂 |

> **我倾向 ①**（P1 阶段）。内核已是纯函数，独立进程的收益在 P1 不存在。**是否同意？**

## 六、生命周期：**只设计一套状态机**（★ 从零的简化）

上一版有两套正交状态机（会话 / 工单），业务岗要同时理解两个字段——这是**复杂度泄漏**。从零我提议**一套主生命周期 + 一个沟通子状态**：

```
queued ──指派──▶ working ──出结论──▶ decided ──确认──▶ executing ──成功──▶ resolved
   │                 │                  │                 │
   │                 │                  │                 └──失败──▶ escalated（人工接管）
   │                 │                  └──需人工/需补证──▶ escalated
   └─────────────────┴── 管理员随时介入 ──────────────────▶ escalated

沟通子状态（挂在 working 下，不影响主生命周期）：
  clarifying（澄清诉求）→ collecting（补齐材料）→ 齐备
```

| 主阶段 | 含义 | 谁能推进 |
| - | - | - |
| `queued` | 已入收件箱，未指派 | 管理员指派 |
| `working` | 智能体处理中 | 智能体 / 管理员介入 |
| `decided` | 已有结论，待确认 | 管理员确认 / 驳回 |
| `executing` | 处置执行中 | 系统 |
| `resolved` | 已完结 | — |
| `escalated` | 转人工（终态之一） | 管理员 / 智能体 |

### 6.1 ★ 奠基性问题 F3：状态机合一是否可接受？

| 选项 | 说明 |
| - | - |
| ① **一套主生命周期 + 沟通子状态**（我的提议） | 业务岗只读 `stage`；沟通细节藏子状态 |
| ② 维持两套正交状态机 | 信息更全，但需理解两个字段 |

> **我倾向 ①**。上一版的两套状态机并没有带来实际收益，只带来理解成本。**请确认。**

## 八、关键接口（三个边界）

### 8.1 智能体 → 决策内核（唯一出口）

```
submit_for_decision(
    case_id,
    claim = { direction, reason, object, amount? }
) -> {
    conclusion,          # auto_pass / auto_reject / request_evidence / to_human
    hit_rules[],         # 命中的规则编号
    details[],           # 逐条依据（给人看）
    needs_human,         # 是否须人工
    replay               # 是否幂等重放
}
```
> **契约**：`direction` **必填**；内核**不认识** case_id（只认 claim + 事实）。

### 8.2 决策内核 → 处置映射（纯函数）

```
resolve_disposal(direction, conclusion) -> action
authorize(action, amount, risk_flags)   -> level (L1/L2/L3)
```

### 8.3 协同层 → 执行层（受控）

```
execute(case_id, action, idempotency_key = case_id) -> { ok, external_ref, error }
```
> **契约**：未授权 → 拒绝执行；失败 → 返回 `ok=false`，**绝不返回假成功**；影子模式 → 只记录不调用。

## 十、能力递进路线（每步可独立演示）

| 里程碑 | 交付能力 | 验收方式 | 计费 |
| - | - | - | - |
| **M1 骨架** | 工单 + 决策内核 + 单工具 + 手动触发 | 命令行跑通"提交→结论" | 否 |
| **M2 沟通** | 对话 + 三件套槽位 + 澄清 | 桩模型多轮澄清 | 否 |
| **M3 取证** | 工具全家桶 + 材料登记 | 桩模型自主取证 | 否 |
| **M4 处置** | 授权分级 + 双闸门（影子） | 影子端到端 | 否 |
| **M5 协同** | 指挥台 + 卷宗 + 介入 | 只凭卷宗可决策 | 否 |
| **M6 合规** | C1—C6 | 六红线可验证 | 否 |
| **M7 真实** | 真实接口 + 资金 | 真实单跑通 | **需单独授权** |

> **成本不是设计前提**：模型**正常使用**，成本由**配置**（开关 + 上限）控制，而非设计假设。
> M1—M6 之所以可以先不花钱，是因为**用桩模型即可完成验收**——不是因为"不许调用模型"。
> （前一版本把"零模型、零现金"写成设计前提，属概念错误：一个从不调用模型的智能体不是智能体。）

### 10.1 ★ 奠基性问题 F4：从哪个里程碑起步？

| 选项 | 说明 |
| - | - |
| ① **M1 骨架**（内核 + 工单，无模型） | 最稳，但短期无"智能"观感 |
| ② **M3 取证**（假设 M1/M2 复用参考代码的经验） | 快，但可能又"跳过验收" |
| ③ M5 协同（指挥台优先） | 可视，但建立在未验收的内核上 |

> **我倾向 ①**——上一版的教训正是"内核没过端到端验收就去做界面"。**请确认。**
